## 1. 현재 결정 적용

현재 확정 업무계약의 본문은 이 문서의 해당 영역 절에만 둔다. 폐기된 비교안과
결정 이유는 Git·`review/` 이력으로만 보존하며 이 정본에서 다시 나열하지 않는다.
현재 계약에서 금지한 구조는 nullable·deprecated·숨김 필드로 우회하여 만들지
않고, 미래 필요만으로 호환 컬럼이나 nullable FK를 추가하지 않는다.

## 2. Wave 경계

Wave별 전체 범위와 유지·제외 경계의 단일 원문은

## 3. 직원

<a id="fr-staff-core"></a>

### 3.1 직원과 재직

- 내부 직원 ID와 재직번호를 분리한다.
- 재직기간은 같은 직원 안에서 서로 겹치지 않는다.
- 퇴사상태는 재직기간 종료일로 계산하고 별도 근무상태를 이관하지 않는다.
- 재입사는 기존 직원에 새 재직기간과 새 재직번호를 생성한다.
- 재직번호 발급은 기존 transaction-safe 번호 카운터를 확장한다.
- 직종과 시스템 업무역할을 분리한다.
- 직종·역할·서비스 제공자격 기간은 해당 재직기간 안에 있어야 한다.
- 재직 범위 자식원장은 `(staff_id, employment_id)` 복합 FK로 같은 직원의
  재직기간만 참조하게 한다.

<a id="fr-staff-sensitive"></a>

### 3.2 민감정보와 연락처

- Wave 0 기존 직원과 bootstrap 직원은 민감정보 행이 0개 또는 1개일 수 있다.
  Wave 1 이후 일반 직원 신규등록은 주민등록번호를 필수로 받아 직원과 민감정보
  행을 한 transaction에서 생성한다.
- 입력은 숫자 13자리 또는 `YYMMDD-XXXXXXX` 형식만 허용한다. 저장 전 하이픈을
  제거해 숫자 13자리로 정규화한다.
- 앞 6자리의 실제 달력날짜와 일곱 번째 숫자의 세기·성별이 `birth_date`와
  `sex_code`에 일치해야 한다. 일곱 번째 숫자 `9/0`은 1800년대,
  `1/2/5/6`은 1900년대, `3/4/7/8`은 2000년대이며 홀수는 남성, 짝수는
  여성으로 판정한다. legacy 호환을 위해 주민번호 checksum 불일치만으로는
  거부하지 않는다.
- 일반 화면의 마스크는 복호화하지 않고 `birth_date`에서
  `YYMMDD-*******`로 만든다.
- 전체번호는 일반 목록·상세·검색·기본 내보내기에 노출하지 않고 관리자
  명시 reveal에서만 일시 제공한다.
- 일반 직원 수정 명령과 수정화면에는 주민등록번호 필드를 넣지 않는다. 필드
  부재는 기존 번호 유지이며 빈 문자열로 삭제·대체할 수 없다. 상세 응답도
  평문을 form default로 돌려주지 않는다.
- 주민등록번호 오등록 정정은 일반 직원 수정과 분리된 HIGH 명령이어야 한다.
  같은 직원의 번호 교체는 현재 PIN·정정사유·`row_version`·전역 중복검사·
  단일 transaction·감사를 요구한다. 다른 직원 사이의 번호 이전이나 직원
  합치기는 별도 정책이 확정되기 전까지 차단한다.
- 초기이관은 안정 legacy mapping으로 같은 사람임이 확정된 행에 한해 같은
  transaction에서 민감정보를 교체할 수 있다. 이름·전화 같은 추정 일치만으로
  교체하지 않는다.
- DB 컬럼·길이·unique 불변조건은
  [`04` §3.2](04_데이터_DB_불변조건_v4.8_PostgreSQL.md), 암호화·key·
  reveal·rotation·평문 금지 protocol은
  [`05` §5.5](05_기술_보안_파일처리_아키텍처_v1.5.md#resident-security), 화면/DOM은
  [`03` §1.3·§3.2](03_UI_API_상호작용_계약_v1.2.md)를 따른다.
- 직원 전화는 화면용 원문과 결정적 정규화 projection을 분리한다.
- 전화 정규화 v1은 한국 번호만 수용한다. 바깥 공백을 제거한 원문은 화면용으로
  보존하고, 공백·하이픈·마침표·괄호만 구분자로 제거한다.
- 파싱은 국제형을 먼저 판정한다. `+82` 또는 `0082` 다음의 선행 `0` 없는
  숫자 8~10자리를 국제형으로 처리한 뒤, `0`으로 시작하는 숫자 9~11자리를
  국내형으로 판정한다.
- 정규화값은 국내 선행 `0`을 제거한 `+82`와 나머지 숫자의 결합이다. 예를 들어
  `010-1234-5678`, `+82 10 1234 5678`, `0082-10-1234-5678`은 모두
  `+821012345678`이다.
- 빈 입력은 원문·정규화값 모두 `NULL`로 만들고, 다른 국가코드·내선·문자·길이
  오류는 422로 거부한다. 정규화값은 unique 식별자가 아니며 일반 응답에는
  기본 노출하지 않는다.
- 정규화 projection은 Wave 3 RFID 후보매칭의 정확 일치 보조키로만 사용한다.

### 3.3 자격·교육·검진·상담

#### 3.3.1 자격증·서비스 제공자격

일반 자격증 사실과 서비스 제공자격 기간은 서로 다른 원장이다.

- `license_type`은 자격종류 코드·표시명을 관리한다. 최초 seed는 다음 3개로
  고정한다.

| code | 표시명 |
|---|---|
| `CARE_WORKER` | 요양보호사 |
| `SOCIAL_WORKER` | 사회복지사 |
| `NURSE` | 간호사 |

- 위 code는 기존 사실이 참조하는 안정 catalog code이므로 일반 업무에서
  변경·삭제하지 않는다. 최초 seed에 등급 구분, 간호조무사, 관리책임자,
  관리책임자(시설장)를 넣지 않는다. 새 자격종류가 필요하면 기존 code의 의미를
  바꾸지 않고 사용자 결정 뒤 새 row를 추가한다.
- `staff_license`는 직원·자격종류·자격번호·발급일을 관리한다. 자격증 유효
  시작일·종료일·만료일은 만들지 않으며, 일반 CRUD는 3개 이상을 허용한다.
- 초기등록 workbook의 자격 2개는 입력범위일 뿐 일반 원장의 최대 개수가 아니다.
- `staff_service_qualification_period`는 재직기간별 서비스 제공 가능 기간의
  안정 ID를 제공한다. 직원·재직·서비스종류·시작일·선택 종료일을 가지며
  선택 `source_license_id`로 같은 직원의 자격증 사실을 근거로 연결할 수 있다.
- 자격증만 보유하고 서비스 제공자격 기간이 없는 상태와, 한 자격증을 재입사한
  여러 재직의 제공자격 근거로 다시 사용하는 상태를 모두 허용한다.
- 서비스 제공자격 기간은 자격증 유효기간이 아니며 해당 재직기간 안에 완전히
  포함되어야 한다. 재직기간 단축·무효화의 역방향 검사도 같은 불변조건을
  보장하고, 부모·자식을 한 transaction에서 함께 정정하는 것은 허용한다.
- 일반 자격증 CRUD와 서비스 제공자격 기간 CRUD는 API·OpenAPI·UI 탭·오류코드를
  분리한다. 자격증 삭제가 아니라 무효화/대체를 사용하며, 근거 자격증을
  무효화해도 제공자격 기간을 자동종료하지 않고 명시적 정정 절차를 거친다.

#### 3.3.2 교육

교육 seed는 다음 8개로 고정한다.

| code | 표시명 | cycle |
|---|---|---|
| `NEW_HIRE_ORIENTATION` | 신규직원교육 | `ON_HIRE` |
| `ELDER_RIGHTS` | 노인인권 | `HALF_YEAR` |
| `DISABLED_ABUSE` | 장애인학대 신고의무자교육 | `ANNUAL` |
| `ELDER_ABUSE` | 노인학대 신고의무자교육 | `ANNUAL` |
| `SEXUAL_HARASSMENT` | 직장 내 성희롱 예방교육 | `ANNUAL` |
| `WORKPLACE_BULLYING` | 직장 내 괴롭힘 예방교육 | `ANNUAL` |
| `PRIVACY` | 개인정보보호교육 | `ANNUAL` |
| `CONTINUING_EDUCATION` | 보수교육 | `BIENNIAL` |

- 신규직원교육은 재직기간마다 `NEW_HIRE_ORIENTATION` 1건이며
  `completed` boolean으로만 완료 여부를 관리한다. 재입사하면 새 재직의
  미완료행을 만든다.
- 정기교육 7종은 직원·과목·대상기간 기준이며 재직 ID에 귀속하지 않는다.
  같은 반기·연도에 퇴사 후 재입사해도 같은 완료상태를 유지한다.
- 보수교육은 장기요양기관에서 현재 요양보호사 직종으로 근무하는 직원만
  대상으로 하며, 대상연도와 출생연도의 홀짝이 같을 때 대상이다.
- 자격시험 합격연도부터 2년이 경과한 연도의 12월 31일까지는 면제다.
  시스템은 자격증의 최초 취득연도를 합격연도 증빙값으로 사용한다.
  예를 들어 2023년 취득자는 2025년 말까지 면제되고 2026년부터 대상이다.
- 정기교육도 `completed` boolean만 저장한다. 교육시간·이수일자·이수센터·
  수료증/파일 FK를 만들지 않는다.
- 신규·정기교육의 완료와 완료해제는 매번 행위자·시각·전후값을 audit한다.

#### 3.3.3 건강검진

건강검진은 **검진일 사실만** 저장한다. 검진일이 있으면 해당 대상 검진을 완료한
것으로 판정한다.

- 대상상태 원장, 상태명, 면제, 면제사유, 미완료사유, 검진유형, 결과메모,
  결과지·증빙파일을 만들지 않는다.
- 신규입사자는 입사일의 정확히 1년 전 다음 날부터 입사일 후 1년까지의 검진일을
  제출할 수 있다. 예를 들어 입사일이 2026-08-15이면 2025-08-16 검진부터
  인정한다. 인정되는 검진일이 하나 있으면 그 달력연도에는 추가 제출하지 않는다.
- 기존 직원은 대상연도보다 이전 연도에 입사한 사람이며 연 1회 검진일이 필요하다.
- 기존 직원이 대상연도 12월 30일 또는 그 이전에 퇴사하면 그 해 검진 제출대상이
  아니다. 12월 31일 퇴사는 이 제외에 포함하지 않는다.
- 신규입사자가 입사한 해에 퇴사하면 입사 때 인정된 검진 외 추가 검진을 요구하지
  않는다.
- 재입사는 새 재직 시작일을 기준으로 신규입사자와 동일하게 판정한다.
- 건강검진은 공식 업무카드 업무목록(§9.3 다섯 가지)이 아니다.

<a id="fr-staff-quarterly"></a>

#### 3.3.4 직원 분기상담

직원 분기상담은 직원·달력연도·분기별 **완료 토글**만 관리한다.

- 완료/미완료는 boolean 토글이며 별도 상태 enum을 만들지 않는다.
- 상담일, 처리내용, 미완료사유, 면제상태, 면제사유, 증빙/file FK를 만들지 않는다.
- 직원·달력연도·분기별 행은 최대 1개이며 완료와 완료해제의 행위자·시각·전후값을
  audit한다.
- 이 원장은 Wave 2의 실제 급여제공 기반 요양보호사 교체상담과 다른 업무이며
  API·화면·감사를 공유하지 않는다.

<a id="fr-staff-legacy"></a>

### 3.4 legacy 직원 mapping

- legacy 직원키는 별도 내부 mapping 원장에 둔다.
- 일반 직원 API·OpenAPI·UI·검색·출력에는 노출하지 않는다.
- 구 시스템 별칭·고용형태·계좌·급여·보험·퇴직금·서비스단가·미사용 컬럼과
  과거 건강검진 자료를 초기 이관하지 않는다.

## 4. 수급자·보호자·납부자 선택

### 4.1 수급자

필수값은 **휴대전화뿐**이다. 이름·생년월일·성별·우편번호·주소·메모는
선택이며 자택전화 필드는 만들지 않는다.

- 내부 PK와 화면 수급자번호를 분리한다.
- 수급자번호는 최초 계약 확정 시 transaction-safe하게 한 번 발급한다.
- 최초 계약 전 수급자 등록을 허용한다.
- 재계약·서비스 추가에도 같은 수급자번호를 유지한다.
- 구 등록번호를 새 수급자번호나 주민등록번호로 해석하지 않는다.
- `legacy_recipient_key`, `legacy_attachment_key`는 별도 내부 mapping에만 둔다.
- 질병정보와 기존 비고는 출처를 표시하여 수급자 메모에 합친다.

### 4.2 보호자

- 수급자당 보호자1·보호자2, 최대 2명만 준비한다.
- 이름·관계·전화번호·주소·이메일 다섯 필드는 모두 선택이다.
- 대표 보호자 개념·대표기간·대표 변경이력을 만들지 않는다.
- 생년월일·성별을 신규 Clean 스키마·API·UI에 만들지 않는다.

### 4.3 납부자 선택

- 납부자는 보호자1 또는 보호자2 중 한 명을 선택할 수 있다.
- 어느 보호자도 선택하지 않으면 수급자 본인이 납부자다.
- 별도 납부자 원장·납부자 입력필드·payer type·독립 snapshot을 만들지 않는다.
- 보호자가 삭제되면 그 보호자를 가리키던 납부자 선택은 본인 납부로 돌아간다.

### 4.4 계약서명자 삭제

계약서명자 개념·필드·snapshot·보호자/납부자 연결을 만들지 않는다.

## 5. 인정·등급·혜택·승인금액

### 5.1 인정 본번호·인정기간·등급

- 입력은 `L + 숫자 10자리`이며 소문자 입력은 대문자 `L`로 정규화한다.
- `-100`, `-101`, `-102` 등의 suffix를 제거하고 본번호만 저장한다.
- 한 수급자는 본번호 1개만 소유한다.
- 같은 본번호를 다른 수급자에게 연결하지 않는다.
- 인정 발급일은 신규 필수값이 아니다.
- 같은 수급자의 유효 인정기간은 서로 겹치지 않는다.
- 인정기간마다 등급 `1`~`5` 중 하나를 함께 저장한다.
- `등급기간`, `등급유효기간`, `인정유효기간`은 별도 업무개념이 아니며 모두
  `인정기간`으로 부른다. 별도 등급기간 원장과 등급변경일을 만들지 않는다.
- 인지지원등급과 자유코드를 허용하지 않는다.
- 과거 기간과 무효화·대체 이력을 보존한다.

### 5.2 혜택

고정 코드:

```text
GENERAL
BASIC_LIVELIHOOD
REDUCTION_6
REDUCTION_9
MEDICAL_6
MEDICAL_9
```

- 수급자 생성 transaction에서 `GENERAL`을 정확히 1건 자동생성한다.
- 혜택 시작값은 날짜가 아니라 표시용 원문 텍스트다. 최초 `GENERAL`의 시작값은
  빈 문자열이며 날짜로 파싱·비교·검증하거나 마감·업무카드 계산에 사용하지 않는다.
- 혜택 변경은 현재값을 무효화하고 대체값을 만들며 한 수급자의 현재 혜택은 최대
  1건이다.
- 부담률 수치는 Wave 4 공식 규칙버전에서 확정한다.

### 5.3 지자체 승인 월급여액

- 혜택과 독립된 기간원장이다.
- 수급자·승인금액·시작일·종료일·무효화/대체 이력을 가진다.
- 금액은 원 단위 bigint이다.
- 같은 수급자의 유효 승인금액 기간은 서로 겹치지 않는다.
- 월중 최고금액 적용 계산은 Wave 4이며 Wave 1에서는 계산하지 않는다.

## 6. 인정 전환 삭제

인정 전환 기능·preview/apply API·일괄 transaction·전용 화면을 만들지 않는다.
인정기간, 등급, 계약은 각각 승인된 일반 등록·정정 절차로 관리한다.

## 7. 서비스 계약

서비스 5종과 그룹 3종:

| 그룹 | 서비스 |
|---|---|
| 장기요양 | 방문요양, 방문목욕 |
| 지역돌봄 연계 | 일시재가, 병원동행 |
| 바로돌봄 | 바로돌봄 |

- 서비스별 독립 계약을 만든다.
- 같은 서비스의 유효 계약기간은 겹치지 않는다.
- 같은 그룹의 서로 다른 서비스는 함께 이용할 수 있다.
- 서로 다른 그룹의 계약기간은 겹치지 않는다.
- 계약 시작일만 필수다.
- 종료일·급여개시일·종료사유는 선택이다.
- 급여개시일은 참고정보이며 누락이 후속 업무를 차단하지 않는다.
- 종료사유는 자유입력·빈 값 허용이며 `사망`은 제안값일 수만 있다.
- 별도 퇴소일을 만들지 않는다.
- 종료된 계약은 재활성화하지 않고 재이용 시 새 계약을 만든다.
- `contract_no`는 기본 Clean 스키마에 만들지 않는다.
- 향후 계약번호가 필요하면 별도 사용자 승인 뒤 nullable 외부참조로 추가한다.

## 8. 배정

### 8.1 요양보호사 배정

- 서비스 계약별 기간배정이다.
- 일반·가족요양을 구분하고 가족요양 관계 snapshot을 보존한다.
- 일정일 기준 유효 배정을 조회할 수 있다.
- 같은 계약·직원의 유효 배정기간은 겹치지 않는다.
- 여러 일반 제공자의 동시배정은 허용한다.
- 배정변경만으로 직원교체 상담 케이스를 만들지 않는다.

### 8.2 사회복지사·간호사 월 배정

- 방문요양과 방문목욕을 합쳐 수급자·서비스월당 현재 전문직 담당은 1명이다.
- 사회복지사와 간호사는 같은 담당 역할이며 직종 이름만 다르다. 역할별로 두 명을
  동시에 배정하지 않는다.
- 월중 변경을 허용하고 변경 전후 history를 보존한다.
- 서비스월 안의 담당 공백일을 허용하며 그 날짜의 조회 결과는 `담당 없음`이다.
- 배정 시 담당자가 사회복지사 또는 간호사 직종인지 검사한다.
- 실제 방문자와 월 담당자 일치판정은 Wave 3에서 다룬다.

## 9. Wave 2 확정 기능계약

Wave 1 구현과 분리하되 다음 정책은 Wave 2 Clean 입력으로 고정한다.

### 9.1 급여계획서

- 통보일·적용 시작일·적용 종료일을 저장한다.
- 작성일·계획서번호를 신규 업무필드로 만들지 않는다.
- 통보월 1~6월은 같은 해 12월 31일, 7~12월은 다음 해 6월 30일이
  기본 종료일이다.
- 연결 계약 종료일과 적용 인정 종료일 중 더 빠른 날로 cap한다.
- 기간 불일치(연결 계약·인정 종료일 cap 초과)나 연결자료 부족(해당 시점 유효
  인정기간 없음)은 저장을 거부한다. 경고 후 저장을 허용하지 않는다.
- 계획서 정정(replacement)은 같은 수급자의 다른 계약으로 바꿀 수 있다. 서로 다른
  수급자를 가리키는 replacement 연결은 허용하지 않는다. 이는 3A의 선언형 DB
  불변조건이다. 운영 원장은 내부 `recipient_id`를 가지며 `(recipient_id,
  recipient_contract_id)`와 `(recipient_id, replacement_service_plan_notice_id)`
  복합 FK의 최종 transaction 상태로 직접 SQL·동시성 변경까지 거부한다.
- 작성마감일(다음 계획서를 새로 작성해야 하는 기한)은 지난 통보일로부터
  6개월 뒤이며, 연결 계약 종료일과 그 시점 유효 인정 종료일 중 가장 빠른
  날짜로 cap한다(2026-08-09 결정).
- 공식 카드의 `인정만료`는 인정기간 종료일 D-100, `계약만료`는 계약 종료일
  D-45, `계획서통보`는 작성마감일 D-45에 발생한다. 작성마감일 D-100 업무는
  만들지 않는다.

### 9.2 실제 급여제공 기반 직원교체

- 수급자·서비스별 실제 급여제공 순서에서 직전 제공자와 새 제공자를 비교한다.
- 기준일은 새 직원의 첫 실제 급여제공일이다.
- 서비스 공백이 있어도 가장 최근 실제 제공자를 직전 직원으로 사용한다.
- Day 1을 포함하여 기한은 첫 제공일 +13일이다.
- Day 14 재교체는 미완료 이전 케이스를 예외 종결하고 Day 15는 적용하지 않는다.
- 하루 대체근무도 같은 규칙을 적용하며 전용 상태를 만들지 않는다.
- 실제근무 정정·무효화 후 재판정할 수 있어야 한다.
- 실제 급여제공 원장은 Wave 3 소유다. 그 원장과 정정 event 계약이 준비되기 전에는
  `직원교체상담` 카드 자동생성기를 만들지 않는다.

### 9.3 공식 업무카드와 개인 할 일

- 공식 업무카드에 들어갈 수 있는 업무목록은 다음 다섯 가지뿐이다. 순서와 표기는
  그대로 유지한다.
  1. 인정만료
  2. 계약만료
  3. 계획서통보
  4. 직원교체상담
  5. 신규직원업무
- 다섯 가지 외의 업무목록을 문서에 제안하거나 열거하지 않는다. 다섯 가지 외
  업무목록을 새로 만들거나 추가·삭제하려면 반드시 형님 사전 승인이 필요하다.
- 업무카드에 들어가는 정보는 다음 다섯 가지뿐이다. 순서와 표기는 그대로
  유지한다.
  1. 업무제목
  2. 대상자이름
  3. 상세업무
  4. 마감일
  5. D-day
- 위 다섯 가지 외의 카드 정보·필드·표시항목을 추가·삭제하려면 반드시 형님 사전
  승인이 필요하다.
- 카드에 진행률·상태·퍼센트·`WAITING`·`EXEMPT`를 표시하거나 저장하지 않는다.
- 사회복지사·간호사에게는 본인 담당 카드만 생성·표시한다. 담당자 본인만 카드를
  닫을 수 있다.
- 새로 생기는 공식 카드의 담당자는 호출자가 지정하지 않는다. 현재 세 갱신카드는
  카드의 정확한 `due_date` 업무기준일에 유효하고 무효화되지 않은 월 전문직 담당
  1명으로 서버가 결정한다. 요청 시각·화면 시각·호출자 값으로 대체하지 않으며,
  그 날짜의 담당을 하나로 확정하지 못하면 카드를 만들지 않는다.
- 관리자는 자기 카드가 생성되지 않는다. 모든 사회복지사·간호사의 열린 카드를
  직원별로 묶어 읽으며, 열린 미완료 카드의 담당자만 바꿀 수 있다. 관리자는
  카드를 대신 닫거나 완료하지 않는다.
- 담당자 변경은 카드 ID·업무종류·마감일·발생키·갱신키·대상·내용·닫힘 상태를
  바꾸지 않고 담당 직원과 `row_version`만 바꾼다. 새 담당자는 현재 재직 중이고
  현재 사회복지사 또는 간호사여야 하며, 관리자 계정에 연결된 직원은 받을 수
  없다. 현재 담당자를 다시 고르는 요청은 422이며 audit·`row_version`을 바꾸지
  않는다. 변경 대화상자는 정확히 `업무종류`, `대상자`, `상세업무`, `마감일`,
  `현재 담당자`를 재확인한다.
- 같은 갱신묶음에서 하위 카드가 상위 카드로 교체될 때, 관리자가 수동으로 바꾼
  담당자는 무조건 유지한다. 최초 재배정 요청에서만 재직·직종·관리자 연결을
  엄격히 검사하고, 그 뒤 우선순위 교체에서는 staff 존재·재직·직종·관리자 연결을
  다시 검사하여 수동 override를 버리거나 거부하지 않는다.
- 닫힌 카드는 현재 목록에서 숨기고 감사기록은 보존한다. 재개방·공개 생성·공개
  삭제 API는 만들지 않는다.
- 카드 내부 발생키는 같은 원천·같은 갱신묶음의 중복을 막는 서버 내부값이며
  화면에 표시하지 않는다.
- 같은 수급자·같은 갱신 목표일에 여러 조건이 겹치면 `인정만료 > 계약만료 >
  계획서통보` 우선순위로 카드 1건만 둔다. 열린 하위 카드가 먼저 생긴 뒤 상위
  조건이 확인되면 같은 transaction에서 하위 카드를 닫고 상위 카드로 교체한다.
- 대상자 이름이 비어 있으면 카드와 목록에는 정확히 `미입력`으로 표시한다.
- `신규직원업무`는 발생조건을 형님이 별도로 승인하기 전 자동생성하지 않는다.
- 시스템 판정으로 생긴 공식 업무카드와 사용자가 작성한 개인 할 일은 데이터·API·
  화면에서 분리한다. 공식 업무카드는 Dashboard에만 표시하고, 개인 할 일은
  `사회복지사` 메뉴의 달력형 일정표에만 표시한다. Dashboard에는 개인 할 일을
  표시하지 않는다.
- 개인 할 일 최종 규칙:
  - 완료는 별도 상태명/enum을 만들지 않고 토글 방식으로 처리한다. 완료된 줄은
    회색의 연한 글씨로 표시한다.
  - 삭제는 완전 삭제다.
  - 순서는 사용자가 드래그해서 직접 변경한다.
  - 생성·수정·완료 토글·삭제·조회는 생성자 본인만 가능하다. 로그인한 다른
    사람과 관리자에게 보이지 않는다.
  - 관리자 대행은 없다.
  - `사회복지사` 달력형 일정표 편집창은 로그인 사용자별로 한 번에 하나만 연다.
    우회된 중복창의 오래된 저장은 서버 version 검사로 409 처리한다.

### 9.4 월간 일정·경고·일괄취소·확정월

- 이름 선택과 월간 일정 진입의 UI 의미는
  [`03` §1.1·§7](03_UI_API_상호작용_계약_v1.2.md)을 따른다.
- 수급자 일정표와 직원 일정표는 같은 일정행을 서로 다른 관점으로 조회한다.
- 재직기간 또는 서비스 제공자격 기간 밖 일정도 draft로 임시저장할 수 있다.
  확정월에는 이런 일정이 한 건이라도 있으면 확정을 거부한다.
- 일정 저장·변경·삭제와 월 확정은 같은 서비스월 제어행을 먼저 잠근다. 여러
  일정행을 잠글 때는 ID 오름차순으로 잠근다.
- 같은 version을 본 동시 요청은 먼저 저장한 요청만 성공한다. 늦은 요청은 최신
  일정 snapshot과 version을 포함한 409를 받으며 자동 병합하지 않는다.
- 409를 받은 화면은 사용자의 미저장 입력을 보존하고 최신자료를 다시 보여준다.
- 같은 계정의 여러 창과 서로 다른 계정의 경합에 같은 규칙을 적용한다.
- 방문목욕 일정에는 서로 다른 요양보호사를 정확히 2명 배정한다.
- 그 밖의 서비스 일정에는 요양보호사를 1명만 배정하며 3인 이상 방문일정은
  프로젝트 범위에 포함하지 않는다.
- 저장 허용 WARNING을 확인한 경우 확인자와 확인시각을 함께 보존한다.
- 일정 일괄취소는 대상 일정·건수 preview와 최종확인을 먼저 제공하고,
  실제근무 증거가 연결된 일정은 대상에서 제외한다. 실제근무 증거 자체는
  Wave 3 소유이며 Wave 2가 가짜 증거를 만들지 않는다.
- 확정월의 일정은 관리자도 바로 변경·취소할 수 없다. 관리자가 확정해제 사유를
  입력한 뒤 처리하며 해제·정정·재확정의 행위자·시각·내용을 보존한다.

## 10. Wave 3 공단 일정·RFID 확정 계약

- 용어는 `공단 일정 엑셀`을 사용한다. 청구 전 자료는 계획 일정, 청구 뒤 잠긴
  월의 자료는 확정 일정으로 구분한다.
- 기본 파일명은 공단 일정 `일정계획_YYYYMM.xlsx`, RFID
  `실시간전송내용.xlsx`다. 운영체제가 붙인 `(1)`, `(2)`는 업무키가 아니다.
- 공단 원본의 동일 행을 자동삭제하지 않는다. 480분 자료는 240분 수가행
  2개로 표현될 수 있다.
- RFID 입력은 사용자가 대상 날짜를 지정한 하루 snapshot이며 파일 내용으로
  대상일을 다시 검증한다. 같은 날짜의 변경파일은 누적이 아니라 이전
  snapshot을 대체하고, 대체 전 원본과 처리이력은 보존한다.
- 시작전송만 있으면 `종료X · HH:mm`으로 표시한다. 누락자료의 사용자 보완은
  수기일정으로 처리하고 원본과 보완이력을 함께 보존한다.
- 실제 시작·종료의 초 단위 차이를 보존하며 엑셀 총시간의 분 값은 참고값이다.

RFID 계획정정 알고리즘:

1. RFID 원본 시작·종료와 실제초는 불변이다.
2. 방문요양·방문목욕 계획 시작·종료는 5분 단위, 서비스시간은 30분 단위다.
3. RFID가 계획보다 길고 초과가 1,799초 이하이면 기존 서비스시간을 유지한다.
4. 초과가 1,800초 이상이면 가까운 30분 단위 증가후보를 만든다.
5. RFID가 계획보다 짧으면 1초 부족도 정상으로 보지 않고 실제시간 이하의
   30분 단위 감소후보를 만든다.
6. 부족 건은 `ACTUAL_SHORTAGE_YELLOW_DOT`와 부족초를 반환한다.
7. 확정 서비스시간을 유지하는 5분 단위 계획후보 중 RFID 시작·종료 오차 합이
   최소인 후보를 고른다.
8. 후보 동률과 30분 증가후보의 정확한 중간값은
   `REVIEW_PENDING`으로 두고 자동 변경을 0건으로 한다.
9. 계약·인정·배정·시간충돌·수동보호·확정월 검사를 통과해야 새 계획 변경판을
   채택한다.

공단 계획 snapshot은 비교자료이며 실제시간 입력으로 사용하지 않는다.
정정 알고리즘은 규칙버전을 입력받는 순수함수로 구현한다. 자동매칭·대체키·
다건매칭·수가행 그룹화·중간값 정책은
[06 결정현황 §7](06_개발로드맵_결정현황_v1.2.md)의 승인된 W3 결정과 가명
sample expected를 따른다. 실제 workbook sheet·header·열·자료형은 승인된 가명
실형상 profile 없이 임의로 확정하지 않는다.

## 11. 교차웨이브 업무개념 freeze

이 절은 미래 테이블명 목록을 고정하지 않고 후속 Wave가 소비할 **업무 의미**를
고정한다. `IDENTITY`는 정정 뒤에도 같은 대상을 뜻하는 뿌리,
`PERIOD_FACT`는 적용기간을 가진 사실, `REVISION`은 같은 대상의 명시적 버전,
`CURRENT_PROJECTION`은 원장에서 계산한 현재값이다. 실제 Wave 1
테이블·PK·FK 매핑과 제약은 04만 소유한다.

| 업무개념 | 의미 분류 | 정정 뒤 지속·대체 의미 | 후속 사용 |
|---|---|---|---|
| 직원 생애 | `IDENTITY` | 정정·재입사 뒤에도 같은 직원 identity 지속 | RFID 직원매칭·실제근무·방문 |
| 재직 | `PERIOD_FACT` | 재입사는 새 사실, 정정은 기존 사실을 보존하고 무효화·대체 | 재직 유효성·초기등록 |
| 직원 전화 정규화값 | `CURRENT_PROJECTION` | 원문·규칙버전으로 재계산하며 identity가 아님 | RFID 후보매칭 보조만 |
| 일반 자격증 사실 | `IDENTITY` | 선택한 사실 ID는 보존하고 정정은 무효화·대체를 명시 | 서비스 제공자격의 선택 근거 |
| 서비스 제공자격 | `PERIOD_FACT` | 정정·기간변경은 대체 사실과 이력을 남김 | 일정일 제공자격 검증 |
| 수급자 생애 | `IDENTITY` | 계약·인정·연락처 정정 뒤에도 같은 수급자 identity 지속 | 공단·RFID·은행·OCR |
| 인정 본번호 소유권 | `IDENTITY` | 한 수급자 1개·전역 소유권을 유지하며 일반 수정으로 교체하지 않음 | 공단·RFID 수급자 매칭 |
| 인정기간과 등급 | `PERIOD_FACT` | 등급은 인정기간의 값이며 정정은 기존 인정기간을 보존하고 대체 사실을 만듦 | 일정·수가·청구 |
| 혜택 | `REVISION` | 현재값 교체 시 과거 revision을 보존하며 표시 시작텍스트는 날짜 의미가 없음 | 수가·청구 |
| 서비스계약 | `IDENTITY` | 종료 뒤 재이용은 새 계약 identity이며 과거 계약은 지속 | 일정·수가·청구 |
| 서비스 종류 | `IDENTITY` | 확정 code 의미를 유지 | 공단·RFID·계산 |
| 요양보호사 배정 | `PERIOD_FACT` | 정정·종료 뒤 기존 배정사실과 대체관계 보존 | 일정일 배정 검증 |
| 월 전문직 담당 | `PERIOD_FACT` | 월중 변경은 새 기간사실이며 이전 사실 보존 | Wave 3 방문대상 |
| 납부자 선택 | `CURRENT_PROJECTION` | 보호자1·2 선택 또는 선택 없음(수급자 본인) | Wave 4 청구 시점 snapshot의 입력 |

혜택의 현재값·과거값이 Wave 1에서 승인된 `REVISION` 구조다. 다른 업무에 별도
`REVISION`을 추가하지 않는다. `row_version`은 동시성 토큰이고 audit·무효화/대체는
변경근거이므로 위 네 업무개념 분류의 identity가 아니다. `CURRENT_PROJECTION`은
별도 사용자 승인 없이 후속 이력의 FK 대상이나 정본 식별자로 사용하지 않는다.

Wave 1에서 만들지 않는 연결점:

- RFID event/execution FK
- 공단 일정 source row/group key
- service visit/execution
- billing run
- document/filebox/import 역참조 FK와 필수 의존
- OCR run/apply 역참조 FK와 필수 의존

## 12. 공통 API·UI·감사 요구

- 모든 변경 API는 권한·CSRF·`row_version`을 검사한다.
- 업무 오류코드의 도메인 의미는 이 문서가, 공통 봉투·HTTP 상태는
  [05 §3](05_기술_보안_파일처리_아키텍처_v1.5.md#api-contract)가,
  화면 표시는 03이 소유한다.
- OpenAPI를 TypeScript 생성 타입의 기술 원본으로 사용한다.
- 생성 타입을 직접 수정하지 않는다.
- 목록 정렬은 마지막 PK까지 결정적이다.
- 이름 선택·목록 문맥·일정 popup의 UI 계약은
  [`03` §1.1·§7](03_UI_API_상호작용_계약_v1.2.md)을 따른다.
- legacy mapping은 API·OpenAPI·UI·검색·출력에서 제외한다.
- 무효화·대체·기간변경·민감조회는 감사에 남긴다.
- 실제 개인정보를 테스트·fixture·문서에 사용하지 않는다.
