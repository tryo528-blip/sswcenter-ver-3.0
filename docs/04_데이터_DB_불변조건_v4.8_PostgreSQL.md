> 업무 의미: [`02_업무규칙_계약_v1.1.md`](02_업무규칙_계약_v1.1.md)
> 대체: `04_DB_업무구조_최종설계_v4.7_PostgreSQL.md`

## 0. 설계 지위

이 문서는 Wave 0 마지막 revision 뒤에 이어지는 Wave 1 Clean **migration
chain**의 업무구조를 정의한다. Wave 1을 단일 revision 하나로 제한하지 않으며,
적용된 revision은 수정하지 않고 후속 변경은 새 revision으로 추가한다. 기존
Wave 1·2 구현의 deprecated 호환구조는 설계 입력이 아니다.

이 문서의 실행 권위는 Wave마다 다르다.

| Wave | 이 문서가 갖는 권위 | 이 문서가 갖지 않는 권위 |
|---|---|---|
| Wave 0 | 적용된 migration과 실제 PostgreSQL catalog로 확인한 기준 schema | 적용 사실과 다른 재설계 |
| Wave 1 | 실행 가능한 상세 DDL: 테이블·컬럼·자료형·nullability·PK/FK·delete action·CHECK·UNIQUE·exclusion·trigger·deferrability | 구현 중 임의 변경 |
| Wave 2 | 확정 업무계약·교차웨이브 인터페이스·금지사항 | 실제 테이블·컬럼·FK·revision 이름과 상세 DDL |
| Wave 3~5 | 책임·의존방향·보존원칙·금지사항 | 실제 schema object·API path·revision 구조 |

따라서 §1~10의 실제 object 이름은 Wave 0·1에만 실행 권위가 있다. Wave 2
이후의 실제 테이블명·컬럼·FK·revision 구조는 해당 Wave 설계 때 확정하며 이
문서에서 미리 봉인하지 않는다.

```text
Wave 0 마지막 revision
→ Wave 1 Clean revision chain
→ Wave 1 통합 봉인
→ Wave 2 Clean revision chain
```

- 기존 revision ID를 재사용하거나 기존 migration을 수정하지 않는다.
- 과거 branch의 스키마는 비교·회귀 증거로만 본다.
- 새 스키마에는 최신 계약에 없는 호환 필드를 만들지 않는다.
- 미래 테이블을 예상한 nullable FK를 미리 만들지 않는다.

## 2. 공통 PostgreSQL 규칙

### 2.1 스키마·키·시간

- 업무 테이블은 `erp` schema를 사용한다.
- 내부 PK는 bigint identity다.
- 업무번호와 내부 PK를 분리한다.
- 업무일자는 `date`, 사건시각은 `timestamptz` UTC로 저장한다.
- 기간은 양끝 날짜를 포함하는 업무표현을 PostgreSQL 반개구간으로 바꾼
  `[start_date, end_date + 1)` `daterange` projection을 사용한다.
- `end_date`가 NULL이면 상한 없는 기간으로 계산한다.
  PostgreSQL range constructor의 NULL upper bound는 unbounded이므로
  `daterange(start_date, end_date + 1, '[)')`를 사용할 수 있다. 명시적
  `CASE WHEN end_date IS NULL THEN NULL ELSE end_date + 1 END`도 같은 의미다.
  range projection 자체는 NOT NULL로 둔다.
  `end_date IS NULL OR start_date <= end_date`도 CHECK한다.
- 현재 유효행의 중복은 `btree_gist` exclusion constraint로 막는다.
- 무효화행은 exclusion predicate에서 제외한다.

### 2.2 변경·감사

- 수정 가능한 aggregate에는 양의 정수 `row_version`을 둔다.
- 원장 정정은 삭제 대신 `invalidated_at_utc`와 `replacement_id`를 사용한다.
- 단, §3.2처럼 1:1 암호화 current slot으로 명시한 민감정보는 같은 행을
  재암호화·version 증가하고 별도 audit event로 정정사실을 남긴다.
- 민감정보는 업무 audit JSON에 넣지 않고 별도 access event를 기록한다.
- 변경 API는 DB transaction 안에서 예상 `row_version`을 비교한다.

### 2.3 제약 이름

DB object exact naming과 prefix의 단일 원문은
[`05` §4.3](05_기술_보안_파일처리_아키텍처_v1.5.md)이다. 이 문서에 적힌 실제
constraint·index·function·trigger 이름은 그 계약을 사용하지만 prefix 규칙을
다시 정의하지 않는다.

<a id="db-staff-sensitive"></a>

### 3.2 `staff_sensitive_identity`

| 컬럼 | 규칙 |
|---|---|
| `staff_id` | PK/FK → `staff.id` |
| `resident_number_ciphertext` | `bytea` NOT NULL·nonempty |
| `resident_number_nonce` | `bytea` NOT NULL, 정확히 12-byte |
| `resident_number_key_version` | integer NOT NULL, 양수 |
| `resident_number_lookup_hmac` | `bytea` NOT NULL, 정확히 32-byte·UNIQUE |
| `encrypted_at_utc`, `updated_at_utc`, `row_version` | 시각·동시성 |

- PK/FK로 직원당 민감정보 행은 0개 또는 1개다. Wave 0 기존 직원과 bootstrap
  직원의 0행은 migration 실패가 아니다.
- `ck_staff_sensitive_identity_ciphertext_nonempty`,
  `ck_staff_sensitive_identity_nonce_length`,
  `ck_staff_sensitive_identity_key_version_positive`,
  `ck_staff_sensitive_identity_lookup_hmac_length`,
  `uq_staff_sensitive_identity_lookup_hmac`를 exact catalog test로 봉인한다.
- 평문 주민등록번호와 마스크 문자열 컬럼을 만들지 않는다. 암호문·nonce·HMAC·
  key version도 공개 API projection에 포함하지 않는다.
- 같은 직원의 승인된 번호 정정은 이 1:1 행을 `FOR UPDATE`로 잠근 뒤
  암호문·nonce·key version·HMAC을 한 transaction에서 교체하고 `row_version`을
  증가시킨다. global HMAC unique를 유지하며 별도 이력행에 암호문을 복제하지
  않는다. 정정사유와 비가역 fingerprint만 감사할 수 있다.
- 기존/신규 cardinality와 입력 업무규칙은
  [`02` §3.2](02_업무규칙_계약_v1.1.md), 암호문 생성·AAD·
  key 관리·reveal·rotation protocol은
  [`05` §5.5](05_기술_보안_파일처리_아키텍처_v1.5.md#resident-security)를 따른다.

<a id="db-staff-employment"></a>

### 3.3 기존 재직·직종·역할의 보강

기존 `staff_employment`의 `(staff_id, id)` unique key를 계속 사용한다.
`staff_position_period`와 `staff_operational_role_period`는
`(staff_id, employment_id)` 복합 FK로 같은 직원의 재직기간만 참조한다.

복합 FK만으로 자식 날짜가 재직기간 안에 있음을 보장할 수 없으므로 다음
deferrable constraint trigger를 명시적으로 둔다.

- `ct_staff_position_within_employment`
- `ct_staff_operational_role_within_employment`
- `ct_staff_service_qualification_within_employment`
- `ct_staff_employment_child_periods_reverse_guard`

각 trigger는 유효 자식기간이 참조 재직기간 안에 완전히 포함되는지 검사한다.
재직 종료일 변경·무효화 시에도 역방향으로 자식기간을 재검사한다. 모두
`DEFERRABLE INITIALLY DEFERRED`로 만들어 부모·자식을 같은 transaction에서
일관된 최종상태로 함께 정정할 수 있게 한다. 대응 function은 동일 stem의
`fn_` 이름을 사용한다.

`license_type`:

`staff_license`:

| 컬럼 | 규칙 |
|---|---|
| `id` | bigint PK, 일반 자격증 사실의 안정 ID |
| `staff_id` | FK → `staff.id` |
| `license_type_id` | FK → `license_type.id` |
| `license_number` | NOT NULL |
| `issued_date` | NOT NULL |
| 무효화·대체·audit·timestamp·`row_version` | 공통 규칙 |

  `uq_staff_license_type_number_active`로 unique다.

- 무효화·대체는 자격증 사실의 정정이며 연결된 서비스 제공자격 기간을
  자동종료하거나 자격증 만료로 해석하지 않는다.

<a id="db-staff-service-qualification"></a>

### 3.5 `staff_service_qualification_period`

이 원장을 적용하는 migration은 §8.1의 3개 `service_group`과 5개
`service_type` catalog가 먼저 존재하도록 같은 migration chain에서 순서를
보장한다. 계약도 같은 catalog를 재사용하며 자격용 catalog를 중복 생성하지 않는다.

| 컬럼 | 규칙 |
|---|---|
| `id` | bigint PK |
| `staff_id`, `employment_id` | 복합 FK → `staff_employment(staff_id,id)` |
| `service_type_id` | FK → `service_type.id` |
| `source_license_id` | NULL 허용, `(staff_id, source_license_id)` 복합 FK |
| `start_date`, `end_date` | 서비스 제공자격 기간 |
| `qualification_period` | generated daterange |
| 무효화·대체·audit·timestamp·`row_version` | 공통 규칙 |

- `id`는 후속 일정·배정 검증이 참조할 안정 ID다.
- `source_license_id`는 근거 사실을 설명하는 선택 연결이며 제공자격 기간의
  존재조건이 아니다. 자격증 없는 제공자격과 재입사 후 같은 자격증 재사용을
  모두 허용한다.
- 유효 기간은 연결 재직기간 안에 완전히 포함되고, 재직기간 단축·무효화의
  역방향 guard도 이를 보장한다.
- 같은 직원·서비스종류의 유효 기간은
  `ex_staff_service_qualification_period`로 겹치지 않는다.
- `care_assignment`가 존재하는 W1E에서는 배정일의 제공자격을 검증하고,
  자격기간 단축·무효화로 유효 배정을 orphan하지 못하는 역방향 guard를
  같은 migration에 추가한다.
- `license_number`와 `issued_date`는 이 테이블에 중복 저장하지 않는다.

#### 3.6.1 교육 catalog·원장

`training_course`는 `code` PK, `display_name`, `cycle_type` CHECK
`IN ('ON_HIRE','HALF_YEAR','ANNUAL','BIENNIAL')`, `active`, `sort_order`를 가진다.
exact seed code·표시명·cycle의 단일 원문은
[`02` §3.3](02_업무규칙_계약_v1.1.md)이며 migration과
catalog test는 그 8행(`ON_HIRE` 1 + periodic 7)을 정확히 seed한다.

`staff_onboarding_training`:

| 컬럼 | 규칙 |
|---|---|
| `id` | bigint PK |
| `staff_id`, `employment_id` | 같은 직원 재직 복합 FK |
| `course_code` | `02` §3.3의 유일한 `ON_HIRE` seed FK |
| `completed` | boolean NOT NULL DEFAULT false |
| 변경행위자·timestamp·`row_version`·무효화/대체 | audit 대상 |

유효행은 재직기간별 최대 1개다. 재직 생성 service가 같은 transaction에서
미완료행을 만들고 재입사 시 새 재직의 새 행을 만든다.

`staff_periodic_training_status`:

| 컬럼 | 규칙 |
|---|---|
| `id` | bigint PK |
| `staff_id` | FK → `staff.id` |
| `course_code` | `02` §3.3의 `HALF_YEAR`/`ANNUAL` 6종 + `BIENNIAL` 1종(`CONTINUING_EDUCATION`) FK |
| period_key | DB column CHECK는 YYYY와 YYYY-H1/H2 두 형식을 허용하며, service/API는 HALF_YEAR에 YYYY-H1/H2, ANNUAL·BIENNIAL에 YYYY를 요구한다. 현재 DB cycle guard는 BIENNIAL을 period_key 형식과 교차검증하지 않는다. |
| `completed` | boolean NOT NULL DEFAULT false |
| 변경행위자·timestamp·`row_version`·무효화/대체 | audit 대상 |

유효행은 `(staff_id, course_code, period_key)`로 unique다.
`employment_id`를 두지 않으므로 같은 기간 재입사 후에도 완료상태를 유지한다.
보수교육(`CONTINUING_EDUCATION`)의 대상자·면제 판정은
[`02` §3.3.2](02_업무규칙_계약_v1.1.md) 원문을 따르며, 이 문서는 새 판정 규칙을 정의하지 않는다.
두 교육 원장 모두 완료·완료해제마다 전후값·행위자·시각을 `audit_event`에
append한다. 교육시간·이수일자·이수센터·문서/file FK는 만들지 않는다.

<a id="db-staff-health"></a>

#### 3.6.2 건강검진 사실·대상상태

`staff_health_check`:

| 컬럼 | 규칙 |
|---|---|
| `id` | bigint PK |
| `staff_id` | FK → `staff.id` |
| `employment_id` | NULL 허용, 값이 있으면 같은 직원 재직 복합 FK |
| `check_date` | NOT NULL |
| `check_type_code`, `result_note` | NULL 허용 |
| 생성행위자·timestamp·`row_version`·무효화/대체 | audit 대상 |

건강검진 사실은 같은 날 복수 record를 허용하므로 `(staff_id, check_date)`를
unique로 만들지 않는다. 같은 직원 검증용 `(staff_id, id)`는 unique다.

`staff_health_check_requirement`:

| 컬럼 | 규칙 |
|---|---|
| `id` | bigint PK |
| `staff_id` | FK → `staff.id` |
| `employment_id` | NULL 허용, 값이 있으면 같은 직원 재직 복합 FK |
| `target_key` | 승인된 대상규칙이 부여하는 안정 text, NOT NULL |
| `target_rule_version_code` | 대상판정 근거 버전, NOT NULL |
| `status` | `COMPLETE`/`INCOMPLETE`/`EXEMPT` CHECK |
| `health_check_id` | NULL 허용, `(staff_id, health_check_id)` 복합 FK |
| `exempt_reason_text` | 조건부 NULL |
| 생성·변경행위자·timestamp·`row_version`·무효화/대체 | audit 대상 |

`ck_staff_health_check_requirement_status_fields`는 다음을 강제한다.

```text
COMPLETE:
  health_check_id NOT NULL AND exempt_reason_text IS NULL
INCOMPLETE:
  health_check_id IS NULL AND exempt_reason_text IS NULL
EXEMPT:
  health_check_id IS NULL AND exempt_reason_text nonblank
```

유효행은 `(staff_id, target_key)`로 partial unique다. `target_key`와
`target_rule_version_code`는 활성 규칙 profile만 생성하는 시스템값이며 공개
생성 API를 두지 않는다. 신규입사자·기존 직원·재입사자의 대상판정은 시행일
기준 공식 원문과 규칙버전이 동결된 뒤에만 활성화한다. Wave 1은 상태 원장,
조회·상태변경 계약과 불변조건을 제공하되 미승인 자동생성·D-day·업무카드를
만들지 않는다. 합성 테스트행은 자동생성 정책의 근거가 아니다.
증빙/file FK는 Wave 5로 미룬다.

## 10. 인정 전환 transaction

### 10.1 preview 입력과 결과

preview hash의 정규 입력집합:

- 수급자와 현재 인정 본번호
- 종료 대상 인정기간과 관련 등급기간
- 종료 대상 장기요양 계약
- 각 계약의 서비스 ID multiset
- 제안 새 인정기간·등급
- 서비스별 대체계약 입력
- 관련 aggregate의 `row_version`
- 무효화·대체·`updated_at_utc` 상태

정렬·날짜·NULL·코드 정규화 규칙을 버전과 함께 고정한 canonical serialization
후 SHA-256을 계산한다. 민감정보나 표시문구는 hash 입력에 넣지 않는다.

### 10.2 apply

```text
수급자·인정·등급·관련계약 SELECT ... FOR UPDATE
→ 현재 입력집합 재구성
→ preview hash constant-time 비교
→ 서비스 multiset·대체계약 완전성 검사
→ 기존 인정·계약 종료
→ 새 인정·등급·서비스별 계약 등록
→ 단일 감사 event
→ COMMIT
```

- stale이면 409이고 변경은 0건이다.
- 누락·중복 대체계약이면 422이고 변경은 0건이다.
- transaction 중 어느 단계든 실패하면 전부 rollback한다.
- preview만으로 DB를 수정하지 않는다.

## 11. 교차웨이브 의미와 Wave 1 실제 매핑

후속 Wave는 테이블명 목록이 아니라 다음 업무 의미를 소비한다. 이 표의 실제
DDL 매핑은 Wave 1에만 권위가 있으며, 후속 Wave의 object 이름을 승인하지 않는다.

| 업무개념 | 의미 분류 | Wave 1 실제 DDL 매핑 | 정정·ID 지속 의미 | 후속 참조대상 |
|---|---|---|---|---|
| 직원 생애 | `IDENTITY` | `staff.id` | 정정·재입사 뒤에도 ID 지속 | `staff.id` |
| 재직 | `PERIOD_FACT` | `staff_employment.id`·재직번호 | 재입사는 새 사실; 정정은 무효화·대체 이력과 새 사실 ID | 사건일에 유효한 재직 사실 ID |
| 직원 전화 정규화값 | `CURRENT_PROJECTION` | `staff.phone_normalized` | 원문·규칙버전으로 재계산; ID 지속 개념 없음 | 후보매칭 값만, FK 대상 아님 |
| 일반 자격증 사실 | `IDENTITY` | `staff_license.id` | 선택했던 사실 ID는 보존; 정정은 무효화·대체를 명시하며 제공자격을 자동종료하지 않음 | 명시적으로 선택한 유효 자격증 사실 ID |
| 서비스 제공자격 | `PERIOD_FACT` | `staff_service_qualification_period.id` | 기간 정정은 기존 사실 보존·대체 사실 생성 | 사건일에 유효한 제공자격 사실 ID |
| 수급자 생애 | `IDENTITY` | `recipient.id`·`recipient_no` | 같은 사람 identity 지속; 번호는 최초 계약 때 1회 부여 뒤 불변 | `recipient.id`, 표시·외부업무에는 `recipient_no` |
| 인정 본번호 소유권 | `IDENTITY` | `recipient_certification_identity.recipient_id`·`certification_number` | 수급자 1:1·전역 unique; 일반 수정으로 다른 본번호 교체 금지 | 수급자 identity와 canonical 본번호 |
| 인정·등급·혜택·승인금액 | `PERIOD_FACT` | 각 `*_period.id` | 정정은 기존 기간사실 무효화·대체와 새 사실 ID | 업무 사건일에 유효한 기간사실 ID |
| 서비스계약 | `IDENTITY` | `recipient_contract.id` | 종료 뒤 재이용은 새 계약 ID; 과거 계약 ID 지속 | 해당 업무를 발생시킨 계약 ID |
| 서비스 종류 | `IDENTITY` | `service_type.id`·`code` | seed 재실행과 표시명 변경에도 code 의미 유지 | `service_type.id`, 계약에는 안정 code 의미 |
| 요양보호사 배정 | `PERIOD_FACT` | `care_assignment.id` | 정정·종료는 기존 사실과 대체관계 보존 | 사건일에 유효한 배정 사실 ID |
| 월 전문직 담당 | `PERIOD_FACT` | `monthly_professional_assignment.id` | 월중 변경은 새 기간사실, 이전 사실 보존 | 사건일에 유효한 담당 사실 ID |
| 독립 납부자 snapshot | `PERIOD_FACT` | `recipient_payer_snapshot.id` | 보호자와 독립된 기간 snapshot을 무효화·대체 | 청구 기준일에 유효한 snapshot ID |

`REVISION`은 같은 업무대상의 명시적 버전이 실제 승인된 경우에만 사용한다.
Wave 1의 기간사실을 이름만 바꾸어 revision으로 취급하지 않는다. `row_version`은
낙관적 잠금 토큰이고 audit는 변경근거이므로 안정 업무 ID가 아니다.
`CURRENT_PROJECTION`은 후속 이력의 FK 대상이 아니며, 기간사실을 정정해 만든
대체 ID로 과거 참조를 조용히 재지정하지 않는다.

Wave 1에서 금지하는 미래 역참조·필수의존 sentinel:

```text
rfid_event_id
corporation_schedule_source_row_id
service_visit_id
service_execution_id
billing_run_id
document_id
document_version_id
file_blob_id
import_run_id
ocr_run_id
ocr_apply_run_id
```

위 문자열은 부재검사용 대표 패턴이며 미래 schema 이름을 예약하거나 승인하지
않는다. catalog의 FK graph와 nullability, ORM·migration, service·repository·
worker, OpenAPI·생성 TypeScript·UI에서 같은 의미의 미래 역참조나 필수의존도
함께 금지한다. Wave 0에 이미 존재하는 `access_event.generated_document_id`는
FK가 없는 nullable 감사 placeholder이므로 그 이름만으로 FAIL 처리하지 않는다.
새 file/import/OCR 테이블·FK·업무의존을 추가했는지 의미로 판정한다.

## 12. Wave 2·3 경계

이 절의 Wave 2·3 항목은 업무계약·의존방향·금지사항이며 실제 object 이름이나
상세 DDL 권위가 아니다.

Wave 1 migration에 다음을 만들지 않는다.

- 급여계획서 갱신카드·직원교체 상담 case·예외상태
- 일정·확정월·실제 급여제공 evidence
- 공단 일정·RFID source/execution
- 수가·청구·수납
- OCR·일반 파일 연계

Wave 2는 Wave 1 PASS SHA에서 새 migration으로 위 업무 중 Wave 2 범위만
추가한다. 실제근무 수집은 Wave 3에서 연결한다.

Wave 2 migration/API 설계가 보존해야 할 비충돌 의미는 다음과 같다.

- 공식 업무카드와 개인 할 일은 별도 source이며 공식 상태는
  `COMPLETE`/`INCOMPLETE`/`EXEMPT`/`WAITING`이다.
- 공식 카드는 발생이유·기한/D-day와 단계별 완료를 가지며, 전문직 카드는
  Wave 1 월 담당 수급자 범위로 제한한다.
- 방문목욕 일정은 서로 다른 요양보호사 정확히 2명이다.
- 일괄취소는 preview 뒤 적용하고 실제근무 증거가 있는 일정을 제외한다.
- 저장 허용 WARNING은 확인자·확인시각을, 확정월 해제는 사유·행위자·시각을
  불변 이력으로 남긴다.

실제근무 evidence는 Wave 3 소유다. Wave 2 schedule이 exclusion hook을
준비할 수는 있지만 Wave 3 테이블/FK를 nullable 미래구조로 선생성하지 않는다.
계획서 반기 cap과 실제 제공 순서 기반 교체상담의 업무본문은
[`02` §9](02_업무규칙_계약_v1.1.md)을 따른다.
