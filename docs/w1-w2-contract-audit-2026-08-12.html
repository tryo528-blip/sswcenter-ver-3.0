SSWCENTER 3.0 · CONTRACT REVIEW

W1~W2 계약·동시성
충돌 확인

형님이 짚은 내용은 대부분 실제 충돌입니다. 다만 “일정을 자유롭게 넣기”와 W1의 배정·자격 원장은 분리해서 고쳐야 합니다.

확인일 2026-08-12 · 형님 추가확정 2026-08-13 · 검토 보고서 · 정본 변경 없음 · 구현 변경 없음

결론부터

문서만 오래된 문제가 아닙니다.
인정 전환, 건강검진, 분기상담, 수급자·보호자·납부자·서명자, 인정·등급 분리는 현재 DB migration·API·화면·테스트에도 들어가 있습니다. 정본만 바꾸면 코드와 더 크게 충돌합니다.
이미 맞게 바뀐 것도 있습니다.
보수교육은 실제 migration에서 추가되어 총 8개이고, 업무카드의 1/2 완료 진행률 문구는 현재 화면 코드와 테스트에서 이미 제거됐습니다.

형님 지시대로 바꿔야 하는 것

실제 구현 충돌

1. 인정 전환 기능 삭제

현재는 기존 인정·계약을 한꺼번에 끝내고 새 인정·등급·계약을 만드는 preview → 확인 → apply 기능이 정본과 W1D API·화면에 구현돼 있습니다.

변경 의미: 이 자동 전환 기능은 제거합니다. 일반적인 인정기간 등록·수정과 계약 등록·수정까지 없애는 것은 아닙니다.

실제 구현 충돌

2. 건강검진

현재의 COMPLETE / INCOMPLETE / EXEMPT와 면제사유 모델은 폐기 대상입니다.

  • 검진일이 입력되면 완료, 없으면 미완료
  • 면제 상태·면제 사유 없음
  • 실제 결과지 파일은 ERP에 등록하지 않음
  • 의무가 없는 사람은 EXEMPT로 남기는 대신 대상 목록에서 제외

대상 원칙: 신규·재입사는 입사 기준 1회, 기존 직원은 연 1회, 기존 직원이 해당 연도 12월 30일까지 퇴사하면 그해 의무 없음, 신규 직원의 입사연도에는 최초 제출 외 추가 의무 없음.

입사 전 검진 인정범위 확정: 입사일의 정확히 1년 전 날짜는 제외하고 그 다음 날부터 인정합니다. 예를 들어 입사일이 2026-08-15이면 2025-08-16 이후 검진일을 인정합니다.

실제 구현 충돌

3. 직원 분기상담

현재의 상담일·내용·미완료사유·면제사유·3상태 계약을 제거하고, 직원 + 연도 + 분기 + 완료 여부(boolean)만 남기는 것으로 읽힙니다.

실제 구현 충돌

4. 수급자·보호자

  • 수급자 생성 필수값은 휴대전화만
  • 자택전화 필드 삭제
  • 보호자는 화면과 저장 모두 최대 보호자1·보호자2
  • 보호자 필드: 이름·관계·전화번호·주소·이메일, 모두 선택
  • 대표보호자와 대표기간 전체 삭제

현재 화면은 두 칸이지만 보호자 이름을 강제하며, DB/API는 보호자 수를 2명으로 제한하지 않습니다. 따라서 화면만 고칠 일이 아닙니다.

부분 구현 충돌

5. 납부자·서명자

독립 납부자 입력필드·snapshot·API는 삭제합니다. 납부자는 보호자1 또는 보호자2 중 하나를 선택하고, 둘 다 선택하지 않으면 수급자 본인입니다.

선택을 저장하려면 내부 연결값 payer_guardian_id 하나는 남아야 합니다. 이것은 별도 납부자 정보가 아니라 “누구를 선택했는지”만 기억하는 값입니다.

계약서의 서명자 이름·관계·전화 필드와 관련 API·화면은 모두 삭제 대상입니다.

실제 구현 충돌

6. 인정기간과 등급 통합

현재는 인정기간과 등급기간을 별도 테이블로 저장합니다. 형님 설명대로라면 인정기간 한 행에 등급을 함께 저장하고, 화면 용어도 모두 “인정기간”으로 통일해야 합니다.

따라서 별도 recipient_grade_period 원장과 “등급기간이 인정기간 안에 포함” 제약은 없어집니다. 등급이 바뀌면 새 인정기간으로 기록하는 구조가 됩니다.

형님 확정

7. GENERAL 자동 생성

정본은 자동생성을 금지하지만, 현재 수급자 기본등록 화면은 본인부담 유형을 기본 GENERAL로 잡고 혜택기간 1건을 함께 저장합니다. 즉 코드와 정본이 이미 어긋납니다.

처음에는 GENERAL로 생성합니다. 시작일은 수급자 등록일을 자동입력하지 않으며, 날짜 의미가 없는 단순 표시 텍스트로만 취급합니다. 날짜 parsing·대소비교·기간제약·마감 계산·업무카드 발생에 사용하지 않습니다.

문서 일부만 낡음

8. 교육 8개

02와 04, migration은 이미 신규직원교육 1개 + 정기교육 7개(보수교육 포함), 총 8개입니다.

WAVE1_CLEAN_TEST_MATRIX의 “exact 7행”과 “정기교육 6종”만 과거 문구이므로 8개 기준으로 정정하면 됩니다.

날짜 로직 충돌

9. 업무카드 D-100 / D-45와 우선순위

  • 인정만료: 인정기간 만료일 기준 D-100
  • 계약만료: 계약기간 만료일 기준 D-45
  • 계획서통보: 작성마감일 기준 D-45
  • 같은 수급자의 같은 갱신 묶음에서는 인정만료 → 계약만료 → 계획서통보 순으로 하나만 발생

현재 역사적 helper는 계획서 작성마감일 하나를 기준으로 D-100과 D-45를 모두 계산합니다. Dashboard 마감 API도 세 종류를 모두 반환하고 우선순위로 하나만 남기지 않습니다.

우선순위 교체 확정: 인정만료 D-100과 계약만료 D-45의 발생일이 달라도 같은 갱신 묶음으로 판정합니다. 하위 카드가 먼저 생긴 뒤 상위 조건이 확인되면 하위 카드를 상위 카드로 교체하여 최종적으로 한 장만 남깁니다.
현재 화면은 이미 충족

10. 진행률·다가오는 마감일

업무카드의 1/2 완료 진행률 문구는 현재 화면에서 이미 제거되어 있습니다. 대기메모만 낡았습니다.

다가오는 마감일은 화면의 남는 세로영역 전체를 사용하고 한 화면에 최소 15건 이상 보이게 합니다. 실제 세로영역을 넘는 경우에만 페이지 이동을 생성합니다.

설명 1 · “월별 전문직 1명”이란?

현재 계약은 다음 네 가지를 묶어 담당자를 찾지만, 형님 확정에 따라 이 구조를 바꿉니다.

수급자 1명
방문요양+방문목욕
특정 월
전문직 담당 1명

확정: 한 수급자가 방문요양과 방문목욕을 함께 이용해도 두 서비스를 합쳐 전문직 담당자는 한 명입니다. 사회복지사·간호사는 담당 배정에서 같은 역할이며, 직원의 실제 직종 명칭만 각각 유지합니다.

월중에 A에서 B로 바꾸면 현재 담당은 B 한 명이고 A의 과거 담당 이력은 남깁니다.

현재 이 월별 전문직 배정은 정본 설계에만 있고 실제 migration/API는 아직 없습니다.

설명 2 · 배정·자격과 일정은 다릅니다

배정기간은 “이 수급자를 담당하는 직원”, 제공자격 기간은 “이 직원이 이 서비스를 제공할 자격이 있는 기간”, 일정은 “특정 날짜·시간에 방문할 계획”입니다.

“재직기간 밖에도 일정을 시험 입력할 수 있어야 한다”는 요구 때문에 배정·자격 원장의 재직기간 제약까지 없애면, 퇴사자가 정상 담당자·정상 자격자로 보이는 부작용이 생깁니다.

형님 확정: W1 배정·자격 원장은 그대로 둡니다. W2 일정은 재직·자격 밖이어도 임시입력까지 허용하지만, 해당 행이 하나라도 남아 있으면 확정월 처리를 거부합니다.

설명 3 · W2-07 실제근무 정정 후 재판정

예: 실제 기록상 A 다음 B가 방문해서 “직원교체상담”이 생겼는데, 나중에 B 방문이 오입력으로 삭제되면 그 상담업무가 정말 필요한지 다시 계산해야 한다는 뜻입니다.

  • 정정 event: 어떤 실제근무 기록이 추가·수정·삭제됐는지 알리는 신호
  • 멱등키: 같은 신호가 두 번 와도 상담카드를 두 장 만들지 않게 하는 고유값
  • transaction/worker 경계: 정정 저장과 재계산을 즉시 한 번에 할지, 뒤에서 별도 작업으로 처리할지 정하는 것

단순안: 실제근무 정정 저장과 상담 재판정을 같은 DB transaction에서 처리하고 별도 worker·event·멱등키를 만들지 않습니다. 다만 실제근무 자체가 Wave 3 소유라 지금 W2 구현을 막을 이유는 없습니다.

설명 4 · 서비스 요약

“제공중 서비스”는 오늘 기준으로 유효한 서비스계약의 이름을 수급자 목록 한 칸에 모아 보여 주는 것입니다.

예: 장기요양: 방문요양, 방문목욕
  • 일정 횟수나 실제 방문실적이 아님
  • 담당 직원 요약이 아님
  • 오늘 유효한 계약만 포함
  • 같은 서비스는 한 번만 표시
  • 현재 코드에는 이미 목록 API와 화면 표시가 연결돼 있음

따라서 대기메모의 “서비스 요약 연결 필요”는 현재 코드 기준으로는 낡았습니다. 다만 형님이 원하는 의미가 “계약된 서비스”가 아니라 “실제로 제공한 서비스”라면 Wave 3 데이터가 필요합니다.

동시성 설계 복구 결과

전부 사라진 것은 아닙니다.
공통 정본의 row_version·409 충돌·멱등성·transaction·DB 제약 원칙, W1D/W1E의 행 잠금·기간 exclusion·역방향 guard, 실제 2-connection PostgreSQL 경합 테스트는 현재 파일에 그대로 남아 있습니다.
실제 누락 원인:
폐기된 외부 연동안에 카드용 중복방지·재시도·단일 transaction 상세안이 함께 들어 있었습니다. 새 ERP 단독 계획에는 “충돌 감지”와 “중복생성 방지”라는 요약만 옮겨져, 범용 동시성 설계의 W2 적용방법이 빠졌습니다.
그대로 보존

1. 공통 수정 충돌

수정·완료·삭제·순서변경 요청은 서버 내부 row_version을 비교합니다. 먼저 바꾼 요청만 성공하고 늦은 요청은 409를 받습니다. 화면은 사용자 입력을 지우지 않고 최신값을 다시 읽어 충돌을 알려야 합니다.

이 값은 서버 내부 제어값이며 업무카드에 보이는 여섯 번째 정보가 아닙니다.

ERP 전용으로 복구

2. 공식 카드 중복생성과 우선순위 경합

같은 수급자의 같은 갱신 묶음에 여러 scheduler가 동시에 들어와도 한 장만 생겨야 합니다.

수급자·갱신묶음 잠금
후보 전부 재계산
인정 > 계약 > 계획서 선택
DB 중복제약으로 최종 방어

단순 “같은 날” 비교가 아니라 서버 내부의 동일 발생 묶음 기준이 필요합니다. 내부 발생키 사용은 형님이 승인했으며, 정확한 키 구성만 후속 DDL 계약에서 봉인합니다.

ERP 전용으로 단순화

3. 재시도 멱등성

폐기된 외부 연동용 credential·cursor·변경피드·cache·command receipt는 되살리지 않습니다. 브라우저 전용 ERP에서는 더 단순하게 처리할 수 있습니다.

  • 완료 토글 UI는 API에 “반대로 바꿔라”가 아니라 원하는 최종값을 보냄
  • 같은 요청이 다시 와도 최종값이 같으므로 두 번 뒤집히지 않음
  • 완전삭제는 이미 없는 행을 다시 지워도 같은 최종결과가 되게 함
  • 자동 카드 생성은 동일 발생키의 DB UNIQUE로 한 번만 저장
형님 확정 + 일정 권장안

4. 개인 할 일과 공용 일정은 다르게 해결

개인 할 일: 로그인 사용자별로 `사회복지사` 달력 편집창을 한 번에 하나만 열 수 있게 합니다. 두 번째 편집창은 열지 않으므로 정상 사용 중 개인 할 일 드래그 경합 자체를 만들지 않습니다. 서버의 version 검사는 비정상 중복창·연결복구 때만 최종 안전장치로 남깁니다.

수급자 일정표·직원 일정표: 두 화면은 복사본이 아니라 같은 일정 원장을 다른 기준으로 보여 주는 projection입니다. 같은 계정인지 다른 계정인지와 무관하게 아래 한 규칙을 사용합니다.

  1. 수정·드래그는 일정 ID, 예상 row_version, 원하는 최종 시간·수급자·직원 값을 보냅니다.
  2. 서버는 해당 월 제어행을 먼저 잠그고 일정행을 잠근 뒤 현재 version과 확정월 여부를 다시 검사합니다.
  3. 먼저 잠금을 얻은 요청만 반영하고 version을 1 증가시킵니다. 늦은 요청은 최신 일정 snapshot을 포함한 409를 받습니다.
  4. 새 일정끼리 동시에 겹치면 DB의 UNIQUE·exclusion 제약이 마지막 한 건만 허용합니다.
  5. 여러 일정의 일괄변경은 일정 ID 오름차순으로 잠가 교착을 피하고 한 transaction으로 처리합니다.
  6. 409 화면은 사용자 입력을 보존하고 최신 원장을 다시 읽습니다. 일정의 시간·직원·수급자는 서로 연관되므로 자동 병합하지 않습니다.

확정월과의 경합: 일정 저장과 월 확정이 같은 월 제어행을 잠급니다. 월 확정 transaction은 잠금 뒤 전체 일정을 다시 읽고 재직·자격 밖 임시일정이 하나라도 있으면 확정을 거부합니다. 따라서 검사 직후 다른 사용자가 부적합 일정을 끼워 넣는 경합도 막습니다.

그대로 보존

5. 기간·부모자식 원장 경합

기간중복은 GiST exclusion, 유효행 중복은 partial UNIQUE, 부모기간 축소와 자식 추가의 동시경합은 결정적인 부모행 잠금 + 양방향 DEFERRABLE guard로 막습니다. 여러 원장을 바꾸는 명령과 감사는 한 transaction에 넣고 실패하면 업무 변경은 0건이어야 합니다.

그대로 보존

6. 늦게 도착한 화면 응답

수급자·직원·탭을 바꾼 뒤 예전 API 응답이 늦게 도착해 새 화면을 덮지 않도록 요청 generation과 대상 ID를 확인하고, 현재 요청이 아닌 응답은 버립니다.

필수 검증

7. 가짜가 아닌 동시성 테스트

순차 호출 두 번으로 대신하지 않습니다. 실제 PostgreSQL 연결 2개를 barrier로 동시에 진입시켜 정확히 1건 성공·1건 충돌을 확인하고, 패자 write 0건·정확한 version 증가·감사 원자성·실패단계별 rollback까지 검사합니다. 일정은 수급자 화면↔직원 화면, 같은 계정↔다른 계정, 일정수정↔월 확정 경합을 각각 검증합니다.

되살리지 않을 것: 삭제 예정인 인정전환 preview → apply 기능 자체와 폐기된 외부 인증·동기화·cursor·cache·change feed는 복구 대상이 아닙니다. 거기서 검증된 잠금·rollback·비동기 응답 차단 패턴만 ERP의 살아 있는 기능에 재사용합니다.

이 절은 유실 복구 감사안이며 아직 정본 계약 추가가 아닙니다. 형님 승인 없이 DDL·API·코드에 반영하지 않습니다.

사회복지사·간호사

  • 로그인한 본인은 자기 공식 업무카드만 볼 수 있습니다.
  • 다른 사회복지사·간호사의 공식 업무카드는 볼 수 없습니다.
형님 확정

관리자

  • 관리자 본인 명의의 공식 업무카드는 생성하지 않습니다.
  • 관리자는 모든 사회복지사·간호사의 공식 업무카드를 한 화면에서 조회합니다.
  • 관리자 기능은 조회 전용이며 담당자를 대신해 처리하지 않습니다.
  • 누구의 카드인지 구분할 수 있도록 직원별 영역으로 묶되, 직원명은 카드 본문의 여섯 번째 정보로 넣지 않습니다.
  • 개인 할 일은 이 관리자 조회에 포함하지 않으며 기존대로 생성자 본인만 봅니다.
별도 진행상황 없음: 관리자 화면도 직원별 공식 업무카드를 그대로 모아 보여 줄 뿐입니다. 진행률·단계·퍼센트·추가 상태를 만들거나 표시하지 않습니다.
