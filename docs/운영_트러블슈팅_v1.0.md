# SSWCenter 운영 트러블슈팅 v1.0

> 지위: 참고 기록, 정책 정본 아님
> 적용: 현재 3.0에서 같은 증상이 실제로 재현될 때만 사용
> 적용 기준: 2026-08-12

## 1. 사용 원칙

- 먼저 현재 3.0의 코드·스크립트·로그·Git 상태를 확인한다.
- 과거 2.2의 테스트 개수, Wave 이름, 포트, 경로를 3.0 기준선으로 사용하지 않는다.
- 과거 handoff/report의 2.2 경로를 열거나 명령으로 재사용하지 않는다.
- 이 문서와 활성 운영지침이 다르면 운영지침을 따른다.
- 해결법을 적용하기 전에 최소 재현과 영향 범위를 기록한다.

## 2. DeepSeek Writer

현재 고정값:

```text
RUNNER=C:\sswcenter\3.0\deepseek_runner\invoke-deepseek-writer.ps1
REPOSITORY_ROOT=C:\sswcenter\3.0
AUTH_FILE=C:\sswcenter\api-keys.local.env
```

### 러너를 찾지 못하는 경우

다음 다섯 파일만 존재하는지 확인한다.

- `.dsw-root`
- `invoke-deepseek-writer.ps1`
- `DeepSeekClient.psm1`
- `EditBatch.psm1`
- `Workspace.psm1`

저장소 내부의 `scripts\invoke-deepseek-workspace.ps1`나 과거 `runner\DeepSeek_Writer`를 fallback으로 사용하지 않는다.

### 인증 실패

- `-EnvFile`은 `C:\sswcenter\api-keys.local.env`만 사용한다.
- 다른 위치를 탐색하거나 프로세스 `DEEPSEEK_API_KEY`로 대체하지 않는다.
- 파일 존재 여부와 `DEEPSEEK_API_KEY` 항목이 정확히 하나인지 확인하되 값을 출력하지 않는다.
- `AUTH_PATH_INVALID`, `FIXED_KEY_INVALID`, `DEEPSEEK_API_KEY_MISSING`을 구분해 보고한다.

### `BLOCKED`인데 파일이 이미 바뀐 경우

1. 상태 문자열만 보고 즉시 재시도하지 않는다.
2. `git diff`, 변경 경로, 파일 내용을 확인한다.
3. 완료조건을 실제 diff와 대조한다.
4. 완성됐으면 테스트·검수로 진행하고, 부분 변경이면 누락만 재작업한다.

### 허용 목록 오류

- `PATH_NOT_READ_ALLOWLISTED`가 나면 필요한 최소 부모 디렉터리를 `read_paths`에 추가한다.
- `write_paths`는 여전히 정확한 파일·디렉터리로 제한한다.
- Task Packet의 경로와 CLI의 `ReadAllowList`·`WriteAllowList`가 일치하는지 확인한다.

`DONE`, `changed_paths`, 요약문보다 현재 파일·diff·실제 테스트 결과가 우선한다.

## 3. 테스트 환경 오염

### `.env` 자동 로딩

- 현재 backend의 settings 로딩 경로와 게이트 스크립트를 먼저 확인한다.
- 환경 파일을 삭제하지 않는다. 격리가 필요하면 대상과 복원 절차를 형님께 보고한 뒤 진행한다.
- 과거 버전의 실패·통과 개수를 현재 기준선으로 사용하지 않는다.

### mypy 범위

`mypy .`를 임의 실행하지 않는다. 현재 `scripts/test.ps1`, CI 또는 승인된 게이트가 지정한 대상만 사용한다. 과거 부채와 신규 오류를 섞지 않는다.

## 4. PowerShell과 TEMP

- `.ps1`의 `#requires`, 사용 문법, 자식 프로세스를 확인해 PowerShell 5.1과 7 중 맞는 실행기를 선택한다.
- DeepSeek 고정 러너는 PowerShell 7을 우선 사용한다.
- `%TEMP%`가 접근 불가능한 시스템 경로라면 현재 사용자 임시폴더를 확인하고 해당 실행 세션에서만 `TEMP`와 `TMP`를 지정한다.
- 실행기 변경 자체를 PASS 근거로 삼지 않고 실제 명령 결과를 다시 확인한다.

## 5. 사라지는 임시 로그

- 실패 재현 전에 로그 위치와 정리 시점을 확인한다.
- 필요하면 실행 중 로그를 저장소 밖 진단 폴더로 복사한다.
- 로그 수집 코드를 제품 저장소에 임시 커밋하지 않는다.
- 키와 인증정보가 포함됐는지 확인한 뒤 검수 자료에 넣는다.

## 6. 반복 수정 누락

- 같은 패턴을 `rg` 또는 `git grep`으로 검색한다.
- 요청 범위 안의 모든 발생 지점을 확인한다.
- 범위 밖 결과는 임의 수정하지 말고 보고한다.

## 7. 정적 정규식 테스트의 한계

- 핵심 계약은 실제 API 결과·DB invariant·런타임 동작을 확인하는 테스트를 우선 검토한다.
- 정적 검사는 빠른 방어층으로 유지하되 최종 진실로 취급하지 않는다.
- 테스트 자체를 바꿀 때는 요구를 약화하지 않았는지 별도 검수를 받는다.

## 8. Git 관련 장애

- 현재 브랜치와 변경사항을 먼저 보고한다.
- 진단을 이유로 `pull`, `checkout`, `reset`, `clean`, rebase, commit, push를 자동 실행하지 않는다.
- Git 변경이 해결에 필요하면 정확한 대상과 이유를 형님께 설명하고 명시 요청을 받은 뒤 실행한다.
