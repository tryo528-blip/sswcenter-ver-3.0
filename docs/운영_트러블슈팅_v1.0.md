# SSWCenter 운영 트러블슈팅 v1.0

> 지위: 참고 기록, 정책 정본 아님
> 적용: 현재 Linux 3.0에서 같은 증상이 실제로 재현될 때만 사용
> 적용 기준: 2026-08-15

## 1. 사용 원칙

- 먼저 현재 저장소 bytes, `ssw-agent status`, Git status, 실제 오류를 확인한다.
- 이 문서와 루트 운영지침이 다르면 운영지침을 따른다.
- 해결법을 적용하기 전에 최소 재현과 영향 범위를 기록한다.
- 과거 Windows wrapper, 장소 선택 호출문, 2.x 경로, 과거 PASS 수치를 현재 기준으로 사용하지 않는다.
- credential 내용은 진단을 이유로도 읽거나 출력하지 않는다.

## 2. Provider 준비 실패

```bash
ssw-agent status
```

- Grok `auth_ready=false`: `ssw-agent auth grok`으로 월구독 계정 device authentication을 다시 수행한다.
- DeepSeek `auth_ready=false`: `ssw-agent auth deepseek`으로 프로젝트 API 키를 숨김 입력한다.
- `installed=false`: 공식 Grok Linux CLI 설치 상태와 `/home/codexctl/.local/bin/grok`을 확인한다.
- `policy_ok=false`: `.grok/config.toml`과 `.grok/sandbox.toml`의 diff를 검수한다. runner의 검증을 끄거나 hash를 임의 변경해 우회하지 않는다.

인증 파일은 존재와 Unix mode만 확인한다. 키·토큰·쿠키를 `cat`, 환경 출력, 로그 복사로 확인하지 않는다.

## 3. Sandbox 실패

```bash
ssw-agent self-test
```

다음 check가 모두 true여야 한다.

- `grok_binary_pinned`
- `worktree_write_allowed`
- `git_write_blocked`
- `system_write_blocked`
- `credential_read_blocked`
- `review_write_blocked`
- `grok_worktree_write_allowed`
- `grok_git_write_blocked`
- `grok_review_write_blocked`
- `grok_system_write_blocked`
- `host_provider_policy_hidden`
- `grok_deepseek_key_read_blocked`
- `path_escape_blocked`
- `git_path_guard`
- `review_write_tools_absent`
- `deepseek_file_tool_write_allowed`
- `empty_file_read_supported`
- `git_internals_not_enumerated`

하나라도 false면 provider 구현·수정을 중단한다. `bubblewrap`, project ownership·mode, `.git` mount, Grok custom profile을 각각 확인한다. sandbox 옵션을 제거해 통과시키지 않는다.

## 4. 실패 결과인데 파일이 바뀐 경우

1. 상태 문자열만 보고 즉시 재시도하지 않는다.
2. `git status --short`, `git diff`, 변경 경로와 현재 파일을 확인한다.
3. 완료조건과 실제 변경을 대조한다.
4. 완성됐으면 테스트·검수로 진행하고, 부분 변경이면 누락 범위만 새 작업으로 수정한다.

provider의 `DONE`, 요약문, error text보다 현재 파일·diff·실제 테스트 결과가 우선한다.

## 5. DeepSeek tool-call 오류

- `DEEPSEEK_PROVIDER_ERROR`: HTTP status와 비밀값이 제거된 짧은 오류만 확인한다.
- `DEEPSEEK_TRANSPORT_ERROR`: DNS·network·endpoint 도달 여부를 확인한다.
- `DEEPSEEK_RESULT_INVALID`: 공식 API schema 변화 여부와 assistant message·tool_calls 구조를 확인한다.
- `DEEPSEEK_TURN_LIMIT`: 범위를 독립적으로 검증 가능한 작은 slice로 나눈다.
- path escape나 `.git` write 거부를 만났으면 경계를 완화하지 말고 project-relative 작업으로 다시 지시한다.

## 6. Grok 실행 오류

- `GROK_AUTH_REQUIRED`: 월구독 로그인을 다시 수행한다.
- `GROK_POLICY_DRIFT`: project policy diff를 검수하고 승인된 변경일 때만 runner pin을 함께 갱신한다.
- `GROK_PROVIDER_ERROR`: CLI stderr의 마지막 비밀정보 없는 오류와 `grok --version`을 확인한다.
- `GROK_RESULT_INVALID`: headless JSON output 형식이 현재 공식 CLI와 맞는지 확인한다.
- native sandbox가 적용되지 않으면 profile을 끄지 말고 실행을 중단한다.

## 7. 테스트 환경 오염

- backend settings 로딩 경로와 gate script를 먼저 확인한다.
- 환경 파일을 삭제하지 않는다. 격리가 필요하면 대상과 복원 절차를 형님께 보고한다.
- `mypy .`처럼 범위가 큰 명령을 임의 실행하지 않고 현재 script·CI·활성 gate가 지정한 대상을 사용한다.
- 과거 버전의 실패·통과 개수를 현재 기준선으로 사용하지 않는다.

## 8. 반복 수정·정적 검사

- 같은 패턴을 `rg` 또는 `git grep`으로 검색한다.
- 요청 범위 안의 모든 발생 지점을 확인한다.
- 범위 밖 결과는 임의 수정하지 말고 보고한다.
- 핵심 계약은 실제 API·DB invariant·runtime 동작을 확인하는 테스트를 우선한다.
- 정적 검사는 빠른 방어층이지 최종 진실이 아니다.

## 9. Git 관련 장애

- 현재 branch와 변경사항을 먼저 보고한다.
- 진단을 이유로 `pull`, `checkout`, `switch`, `reset`, `clean`, rebase, merge, commit, push를 자동 실행하지 않는다.
- Git 변경이 필요하면 정확한 대상과 이유를 형님께 설명하고 명시 지시를 받은 뒤 Codex가 수행한다.
