# W2 공식 업무카드·개인 할 일 구현계획

> 상태: `POLICY_CONFIRMED`
> 기준일: 2026-08-13 KST
> 목적: ERP 내부 공식 업무카드와 개인 할 일을 서로 다른 원장·API·화면으로 구현한다.

## 🚨 형님 승인 절대 게이트

> **형님 승인 없이 어떠한 계약도 추가하거나 삭제하지 않는다.**
> 업무목록 다섯 가지와 카드 정보 다섯 가지 밖의 항목은 구현·문서·테스트에
> 추가하지 않고 형님 승인을 먼저 받는다.

## 1. 원장과 화면 분리

| 원장 | 소유자·권한 | 표시 위치 |
|---|---|---|
| 공식 업무카드 | 서버 판정으로 생성. 담당 사회복지사·간호사가 본인 카드만 닫음 | Dashboard |
| 개인 할 일 | 로그인한 생성자 본인만 생성·조회·수정·완료 토글·삭제·정렬 | `사회복지사` 메뉴 달력형 일정표 |

- 두 원장을 한 행·한 목록·한 API로 합치지 않는다.
- Dashboard에는 개인 할 일을 표시하지 않는다.
- 관리자는 개인 할 일을 볼 수 없고 대신 처리할 수도 없다.
- 브라우저 저장소를 원장으로 사용하지 않는다. 서버 성공 뒤에만 UI 상태를 확정한다.

## 2. 봉인된 공식 업무카드

### 2.1 업무목록 다섯 가지

1. 인정만료
2. 계약만료
3. 계획서통보
4. 직원교체상담
5. 신규직원업무

### 2.2 카드 정보 다섯 가지

1. 업무제목
2. 대상자이름
3. 상세업무
4. 마감일
5. D-day

- 대상자 이름이 비어 있으면 `미입력`으로 표시한다.
- 닫기 버튼은 조작 제어이며 여섯 번째 카드 정보가 아니다.
- 내부 ID·담당자 ID·발생키·`row_version`·닫힘 감사정보는 카드 본문에 표시하지
  않는다.
- 진행률·퍼센트·별도 상태단계·대기·면제 표시를 만들지 않는다.

## 3. 발생·중복·우선순위

| 카드 | 발생일 |
|---|---|
| 인정만료 | 인정기간 종료일 D-100 |
| 계약만료 | 계약 종료일 D-45 |
| 계획서통보 | 급여계획서 작성마감일 D-45 |

- 같은 원천·같은 갱신묶음은 서버 내부 발생키로 중복을 막는다.
- 같은 수급자·같은 갱신 목표일에 겹치면 `인정만료 > 계약만료 > 계획서통보`
  순서로 열린 카드 하나만 유지한다.
- 하위 카드가 먼저 생겼다면 상위 조건 확인 transaction에서 하위 카드를 닫고
  상위 카드로 교체한다.
- `직원교체상담`은 Wave 3 실제 급여제공 원장과 정정 event가 준비되기 전에는
  자동생성하지 않는다.
- `신규직원업무`는 발생시점·담당자·마감일을 형님이 별도 승인하기 전에는
  자동생성하지 않는다.
- 공식 카드 공개 생성·삭제 endpoint는 제공하지 않는다.

## 4. 공식 카드 권한과 닫기

- 현재 직종이 사회복지사 또는 간호사인 직원에게만 담당 카드를 생성한다.
- 신규 공식 카드의 담당자는 호출자가 넘긴 값이 아니라, 카드의 정확한 `due_date`
  업무기준일(현재 세 갱신카드는 원천 정책이 만든 마감일)에 유효한 월 전문직
  담당으로 서버가 결정한다. 요청·화면 시각으로 바꾸지 않으며 그 날짜의 비무효
  담당이 1명으로 확정되지 않으면 실패한다.
- 일반 사용자는 로그인 계정에 연결된 직원의 열린 카드만 조회한다.
- 담당자 본인만 예상 `row_version`을 보내 카드를 닫는다.
- 관리자는 자기 카드가 생성되지 않는다.
- 관리자는 모든 사회복지사·간호사의 열린 카드를 직원별로 묶어 읽고, 열린
  미완료 카드의 담당자만 바꿀 수 있다. 관리자는 카드를 대신 닫거나 완료하지
  않는다.
- 담당자 변경 대화상자는 업무종류, 대상자, 상세업무, 마감일, 현재 담당자를
  다시 확인한다. 새 담당자는 현재 재직 중이고 현재 사회복지사 또는 간호사여야
  하며 관리자 연결 직원은 받을 수 없다. 현재 담당자 선택은 422이며 audit나
  `row_version`을 바꾸지 않는다.
- 담당자 변경은 카드 ID·종류·마감일·발생키·갱신키·대상·내용·닫힘 상태를
  유지하고 `assignee_staff_id`와 `row_version`만 바꾼다. 감사는 실행 관리자와
  변경 전후 담당자 snapshot을 따로 기록한다.
- 같은 갱신묶음의 하위 카드가 상위 카드로 교체되면 수동 지정 담당자를 무조건
  유지한다. 최초 재배정 뒤 staff 존재·재직·직종·관리자 연결을 다시 검사하여
  계승된 override를 거부·교체하지 않는다.
- 닫힌 카드는 현재 목록에서 제외하고 `closed_at`, `closed_by`와 audit를 보존한다.
- 닫힌 카드를 다시 여는 endpoint와 화면 제어는 만들지 않는다. 같은 원천의 새
  occurrence는 새 카드다.

## 5. 개인 할 일

- 제목은 trim 후 비어 있으면 거부한다.
- 완료는 별도 상태 enum 없이 boolean 토글로 저장한다.
- 완료된 줄은 회색의 연한 글씨로 표시한다.
- 삭제는 완전삭제다.
- 사용자가 드래그한 전체 순서를 서버에 저장한다.
- 조회·생성·제목수정·완료 토글·삭제·정렬은 생성자 본인에게만 허용한다.
- `사회복지사` 달력형 일정표 편집창은 로그인 사용자별로 한 번에 하나만 연다.
- 중복창 우회에 대비해 목록 revision을 검사하고 오래된 요청은 최신 목록을 포함한
  409로 거부한다.

## 6. API 계약

### 6.1 공식 업무카드

- `GET /api/v1/official-work-cards`
  - 일반 사용자: 본인 열린 카드만.
  - 관리자: 직원별 그룹의 열린 카드만.
  - 카드 항목은 대화상자에 필요한 현재 담당자를 노출하되, 표시 다섯 정보에는
    넣지 않는다.
- `GET /api/v1/official-work-cards/eligible-assignees`
  - 관리자만. 현재 재직 중이고 현재 사회복지사 또는 간호사며 관리자 계정이
    연결되지 않은 직원만 반환한다.
- `POST /api/v1/official-work-cards/{id}/close`
  - 담당자 본인만.
  - request는 `expected_row_version`을 포함한다.
  - 성공하면 카드는 현재 목록에서 사라진다.
- `POST /api/v1/official-work-cards/{id}/reassign`
  - 관리자만.
  - request는 `expected_row_version`과 `assignee_staff_id`를 포함한다.
  - 동시 변경·닫힘·오래된 화면은 409와 최신 snapshot으로 거부한다.
- 공개 create/delete/reopen operation은 없다.

### 6.2 개인 할 일

- `/api/v1/personal-todos`: 본인 목록·생성·제목수정·완료 토글·완전삭제.
- `/api/v1/personal-todos/reorder`: 전체 ID 순서와 예상 목록 revision을 제출.
- 관리자용 조회·대행 operation은 없다.

### 6.3 공통

- same-origin 세션·CSRF·권한·예상 version을 사용한다.
- OpenAPI를 생성 TypeScript의 기술 원본으로 사용한다.
- 공식 카드와 개인 할 일을 합친 endpoint·응답·union을 만들지 않는다.
- 409는 최신 version/snapshot을 포함하고 UI는 사용자의 입력을 보존한다.

## 7. UI 계약

### Dashboard

- 공식 카드에 다섯 정보만 표시한다.
- 관리자는 직원별 그룹으로 읽고 담당자만 바꾼다. 닫기 제어는 없다.
- 다가오는 마감일은 사용 가능한 세로영역에 페이지당 최소 15건을 표시한다.
- 전체가 15건 이하면 페이지 이동을 숨기고 초과할 때만 표시한다.
- 개인 할 일·진행률·상태 퍼센트를 표시하지 않는다.

### 사회복지사 달력형 일정표

- 로그인한 생성자 본인의 개인 할 일만 표시한다.
- 생성·제목수정·완료 토글·완전삭제·드래그 정렬을 제공한다.
- 완료 줄을 회색의 연한 글씨로 표시한다.
- 공식 카드 D-day나 관리자 대행 제어를 붙이지 않는다.

## 8. transaction·감사

- 카드 내부 발생키에는 unique 방어를 두고 우선순위 교체는 한 transaction이다.
- 카드 닫기는 `row_version` 경쟁에서 정확히 한 요청만 성공한다.
- 개인 할 일 정렬은 소유자 목록을 잠그고 전체 ID 집합이 현재 목록과 정확히
  일치할 때만 적용한다.
- 패자·권한거부·검증실패에는 제품 write와 성공 audit가 남지 않는다.
- 카드 생성·교체·닫기와 개인 할 일 생성·수정·완료·삭제·정렬을 기존
  `audit_event` 규칙에 따라 기록한다. 개인 할 일 완전삭제 뒤에는 업무행이 남지
  않지만 감사행은 보존한다.

## 9. 구현 슬라이스

1. 개인 할 일 서버 원장·API·사회복지사 달력형 일정표를 구현하고 Dashboard의
   개인 할 일 mock/localStorage를 제거한다.
2. 공식 카드 원장·본인/관리자 조회·본인 닫기 API를 구현하고 Dashboard mock을
   실제 API로 교체한다.
3. 인정만료·계약만료·계획서통보 원천을 내부 발생키와 우선순위 transaction에
   연결한다.
4. `직원교체상담`과 `신규직원업무` 생성기는 각 선행조건 승인 전까지 부재검사로
   막는다.

각 슬라이스는 `정본 일치 → RED → 구현 → PostgreSQL/API/OA/DOM GREEN → 독립
read-only 검수` 순서로 진행한다.

## 10. 핵심 수용테스트

- 봉인 다섯 종류 밖 카드 생성 거부와 다섯 표시정보 밖 DOM 부재.
- 본인/타인/관리자 조회·닫기 권한과 CSRF.
- 동시 중복 발생 1건, 우선순위 원자 교체, 동시 닫기 1 success + 1 conflict.
- 닫은 카드 현재 목록 부재·감사 보존·재개방 endpoint 부재.
- 개인 할 일 타인·관리자 비노출, 토글, 회색 표시, 완전삭제, 드래그 정렬.
- 동일 계정 중복창 reorder 1 success + 1 conflict와 최신 목록 반환.
- Dashboard 개인 할 일/localStorage 부재, 다가오는 마감일 15건·overflow pagination.
- OpenAPI 독립 재생성과 생성 TypeScript drift 0.
