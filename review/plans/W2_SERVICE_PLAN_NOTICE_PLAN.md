## 1. 범위

포함:

- 급여계획서 통보일·적용 시작일·적용 종료일 원장.
- 연결 계약·인정기간 coverage와 역방향 무결성.
- 작성마감일 계산.
- 공식 카드 세 원천의 발생일과 우선순위 연결.
- `0020+` 전진 migration, 실제 PostgreSQL, API·OpenAPI, 감사.

제외:

- 공식 업무카드 다섯 종류 외 업무.
- 공개 카드 생성·삭제·재개방.
- 실제근무 원장 없는 `직원교체상담` 생성.
- 형님이 발생조건을 승인하기 전 `신규직원업무` 생성.
- 공용 일정·개인 할 일 구현.

## 2. 급여계획서 계약

1. 계획서는 수급자 서비스계약 하나에 연결한다.
2. 통보일·적용 시작일·적용 종료일을 저장한다.
3. 적용 종료일 기본값은 통보월 1~6월이면 같은 해 12월 31일, 7~12월이면
   다음 해 6월 30일이다.
4. 적용기간은 연결 계약기간과 같은 수급자의 인정기간을 벗어날 수 없다.
5. 계약·인정기간이 없거나 무효이거나 전체 적용기간을 보장하지 못하면 저장을
   거부한다. 경고 후 저장은 없다.
6. 부모 계약·인정기간 정정으로 기존 계획서가 범위를 벗어나지 않도록 최종
   transaction 상태를 검사한다. 부모와 계획서를 한 transaction에서 함께
   올바르게 정정하는 것은 허용한다.
7. 정정은 기존 사실을 무효화하고 대체 사실을 만들어 과거 ID와 감사를 보존한다.
8. 인정의 등급은 인정기간 행의 값이며 별도 등급기간 원장을 조회하지 않는다.

## 3. 작성마감일과 공식 카드

작성마감일은 지난 유효 통보일로부터 6개월 뒤 날짜를 계산한 다음, 연결 계약
종료일과 그 시점의 인정 종료일 중 더 빠른 날짜로 cap한다.

| 카드 | 발생 기준 |
|---|---|
| 인정만료 | 인정기간 종료일 D-100 |
| 계약만료 | 계약 종료일 D-45 |
| 계획서통보 | 작성마감일 D-45 |

- 작성마감일 D-100 업무·카드는 만들지 않는다.
- 같은 수급자·같은 갱신 목표일에 세 조건이 겹치면 `인정만료 > 계약만료 >
  계획서통보` 순으로 한 카드만 연다.
- 하위 카드가 먼저 존재하다 상위 조건이 확인되면 한 transaction에서 하위
  카드를 닫고 상위 카드로 교체한다.
- 같은 원천·같은 갱신묶음은 화면에 보이지 않는 내부 발생키로 중복을 막는다.

## 4. migration과 데이터 안전

- 적용된 `0001~0019` migration은 수정하지 않는다.
- 과거 `0018` 원장과 `0019` 읽기 전용 전환은 역사 원본으로 보존한다.
- 새 쓰기 원장은 `0020+` 전진 migration에서 만들며 과거 DB 데이터를 자동으로
  새 운영 원장에 넣지 않는다.
- 기존 DB는 프로젝트 밖에 custom-format dump, SHA-256, manifest로 보관하고
  별도 DB 복원시험과 주요 count 확인을 마친 뒤 읽기 전용으로 둔다.
- fresh DB 전체 upgrade와 이전 head에서의 upgrade를 모두 지원한다.
- migration 중 기존 인정기간과 별도 등급행을 합쳐야 할 때는 수급자·기간·날짜가
  정확히 1:1 일치하는 경우만 허용하고 나머지는 추측 없이 실패시킨다.
- downgrade로 운영자료를 조용히 삭제하지 않는다. 복구는 검증된 백업 복원을
  사용한다.

## 5. transaction·동시성

- 모든 변경은 권한·CSRF·예상 `row_version`을 검사한다.
- 부모 계약·인정기간과 계획서 행을 여러 개 잠그면 안정 PK 오름차순을 사용한다.
- 동일 version을 본 동시 변경은 먼저 commit한 요청만 성공한다.
- 패자는 최신 계획서 snapshot과 version을 포함한 409를 받고 부분 write·부분
  감사는 0건이어야 한다.
- 카드 생성·교체와 원천 변경은 중복키와 우선순위를 같은 transaction에서 검사한다.

## 6. API·표시 경계

- 계획서 API는 업무 중심 request/response와 공통 오류봉투를 사용한다.
- OpenAPI를 생성 TypeScript의 기술 원본으로 사용한다.
- 계획서 화면은 기간 불일치·부모 충돌·409에서 사용자 입력을 보존한다.
- 공식 카드에는 업무제목·대상자이름·상세업무·마감일·D-day만 표시한다.
- 대상자 이름이 비어 있으면 `미입력`으로 표시한다.
- 카드 진행률·상태·퍼센트·`WAITING`·`EXEMPT`·재개방을 추가하지 않는다.

## 7. RED→GREEN 순서

1. `WAVE2_SVC_PLAN_NOTICE_TEST_MATRIX.md`의 `SEM/ABS`를 먼저 RED로 고정한다.
2. `0020+` migration과 ORM을 작성하고 fresh/upgrade PostgreSQL을 GREEN으로 만든다.
3. service·API·감사·409를 구현한다.
4. OpenAPI와 생성 TypeScript를 재생성하고 drift 0을 확인한다.
5. 공식 카드 엔진과 연결해 내부 발생키·우선순위·원자 교체를 검증한다.
6. 실제 2-connection 동시성, backup/restore, 독립 read-only 검수를 수행한다.

## 8. 완료조건

- 정본·계획·matrix 사이에 D-100/D-45 의미가 하나로 일치한다.
- 별도 등급기간·인정 전환·작성마감일 D-100 로직이 없다.
- 계약·인정기간 정정과 카드 우선순위가 PostgreSQL에서 원자적으로 보호된다.
- 제거된 필드·상태·경로가 OpenAPI·생성 타입·UI·테스트 fixture에 남지 않는다.
- 새 운영 DB와 보관 DB가 물리적으로 분리되고 복원 증거가 존재한다.
